## Context

当前 `streamers` 表和 `Streamer` DTO 只保存主播名称、来源身份、直播状态和监听状态。后续切片 LLM 需要知道主播更偏向“带货”“搞笑”“知识科普”还是其他内容类型，才能在同一份 ASR 文本中重点寻找不同类型的句子，但现有模型没有可复用的主播语义元数据。

本变更跨越 SQLite、repository、主播创建/编辑服务、Tauri DTO、React 表单和浏览器演示模式。标签必须保持本地、用户可控、可排序并支持主播身份合并，同时不能改变当前监听 worker、录制、视频预览和正在规划的用户触发 ASR 流程。本次只提供标签和结构化上下文，不生成 Prompt，也不调用任何模型。

## Goals / Non-Goals

**Goals:**

- 每个主播支持最多 10 个独立、可排序的标签。
- 标签包含短名称和可选的 Prompt 指导，名称可以直接使用“带货”“搞笑”等语义。
- 标签随主播创建、编辑、查询、归档、恢复和无历史身份合并正确保存。
- 现有主播在无数据损失的 migration 后获得空标签集合。
- 前端支持标签维护、排序、徽章展示和已有标签名称建议。
- 提供稳定的 `StreamerPromptContext` 结构，供后续切片变更读取。
- 标签操作不触发主页解析、直播间检查、worker 重建、FFmpeg 或模型调用。

**Non-Goals:**

- 不生成切片 Prompt，不调用 LLM，不判断精彩，不提取句子，不创建切片。
- 不修改或扩展当前 `add-user-triggered-ai-asr` 活动变更。
- 不自动从个人主页、直播内容或转写文本推断标签。
- 不提供全局标签模板管理、标签筛选、颜色、图标、导入或导出。
- 不在本变更中创建 AI 项目标签快照；后续 AI 项目在创建时复制 `StreamerPromptContext`。

## Decisions

### 1. 使用每主播关系表，不使用 JSON 列或全局标签实体

新增 `streamer_tags` 表，每条记录只属于一个主播：

- `id INTEGER PRIMARY KEY`；
- `streamer_id INTEGER NOT NULL REFERENCES streamers(id) ON DELETE CASCADE`；
- `name TEXT NOT NULL`；
- `normalized_name TEXT NOT NULL`；
- `prompt_guidance TEXT NULL`；
- `sort_order INTEGER NOT NULL`；
- `created_at TEXT NOT NULL`；
- `updated_at TEXT NOT NULL`。

建立 `(streamer_id, normalized_name)` 唯一索引和 `(streamer_id, sort_order)` 唯一索引。标签按 `sort_order, id` 返回。

每主播关系表允许两个主播使用同名标签但配置不同指导，也避免修改全局模板时意外影响所有主播。JSON 列虽然写入简单，但难以建立唯一约束、进行确定性合并和查询标签建议，因此不采用。全局 `tags` 加关联表更适合成熟的标签管理产品，但当前没有全局编辑、统计或颜色等需求，会增加不必要的生命周期和冲突语义，因此暂不采用。

### 2. 后端统一规范化和校验，前端只提供即时提示

新增 `StreamerTagInput`、`StreamerTag` 和共享校验函数。规范化名称使用 Unicode 首尾空白清理和适合当前 UI 的大小写无关比较键；保留用户原始可见大小写。名称限制 1–24 个字符，指导限制 500 个字符，拒绝控制字符和同一主播内重复名称。

前端复用相同上限提供即时提示，但 Tauri command 和 repository 入口必须重新校验，避免浏览器演示状态或旧客户端绕过规则。错误使用稳定错误码并指向 `tags` 字段，不回显完整非法内容。

备选方案是在 SQLite 触发器中完成全部校验，但字符长度、控制字符和规范化规则难以与 Rust/TypeScript 保持一致，因此数据库只承担非空、唯一和外键约束。

### 3. 使用事务性整组替换保证顺序和失败回滚

创建和编辑请求携带完整有序标签数组。repository 在事务中完成：

1. 校验完整输入；
2. 更新或创建主播；
3. 删除该主播旧标签；
4. 按数组顺序写入新标签；
5. 提交后返回包含标签的最新主播 DTO。

标签数量小且上限固定为 10，整组替换比逐项 patch 更容易保证排序唯一性和原子回滚。只修改标签时，`streamer_service` 识别来源和名称未变化，不停止 worker、不发起 resolver 请求；监听开关变化仍使用现有控制流程。

### 4. 列表查询批量加载标签，避免每行一次查询

单个主播查询可以直接加载其标签。主播列表和 dashboard 先查询主播集合，再用一次 `WHERE streamer_id IN (...)` 查询批量加载标签并按主播 ID 分组，避免主播数量增加后出现 N+1 查询。

`Streamer` DTO 增加 `tags: Vec<StreamerTag>`，序列化为 `tags` 数组；已有记录和无标签主播稳定返回空数组而不是 `null`。前端类型与浏览器演示 API 使用同一结构。

### 5. 通过现有标签记录生成本地输入建议

不创建全局标签表。repository 提供只读的标签名称建议查询，从现有未归档和已归档主播标签中按最近使用或名称返回去重后的有限列表。建议只帮助输入，不会自动写入标签，也不会共享或覆盖其他主播的 Prompt 指导。

备选方案是内置“带货”“搞笑”等固定标签字典，但第一版无法覆盖不同垂类，也会把产品预设误认为模型规则，因此不采用。

### 6. 标签排序使用明确按钮，不增加拖拽依赖

添加/编辑弹窗以标签项列表展示名称、可选指导、删除按钮和上移/下移按钮。数组顺序直接映射 `sort_order`。这种方式支持键盘和辅助技术，也不需要新增拖拽依赖。

主播表格只展示紧凑名称徽章，超出可用空间时显示前若干项和“+N”；详情区域展示完整顺序和可选指导。标签不得取代直播状态、监听状态或主要操作。

### 7. 身份合并在同一数据库事务中合并标签

当无历史临时个人主页主播合并到已有主播时：

1. 保留目标主播原标签和顺序；
2. 按来源顺序追加规范化名称不存在的标签；
3. 同名标签目标指导为空时补充来源指导；
4. 双方指导均非空且不同时保留目标配置；
5. 超过 10 个时优先保留目标标签，再追加来源标签到上限；
6. 完成标签处理后再删除临时主播。

该逻辑与主播身份绑定处于同一事务，任何写入失败均保留两条原记录。标签差异不是身份冲突，不得阻止已有合并规则。

### 8. `StreamerPromptContext` 是只读数据契约，不是 Prompt 生成器

新增结构：

```text
StreamerPromptContext
├── streamer_id
├── streamer_name
└── tags[]
    ├── name
    ├── prompt_guidance
    └── priority
```

repository 或独立纯函数根据当前主播 DTO 生成该结构。它不包含系统 Prompt、模型参数、转写文本或调用入口，也不会触发后台任务。后续 AI 项目创建时负责复制该上下文作为快照，确保主播标签后续修改不改变历史分析结果。

标签和指导属于用户配置数据。未来 Prompt 构建器必须使用结构化、明确分隔的上下文区块，并保持系统安全规则和输出约束具有更高优先级。本变更只通过序列化测试固定契约。

### 9. migration 版本在实施时与其他活动变更协调

当前还有独立 ASR 活动变更，可能同时规划 SQLite migration。实施本变更时先读取最新 `schema_migrations`，选择当时未使用的下一个版本，不在提案阶段硬编码版本号。migration 只新增标签表和索引，不重建 `streamers`，因此回滚可以停止读取标签表并保留数据，无需降级删除。

## Risks / Trade-offs

- [标签自由输入导致同义词分散，例如“带货”和“直播带货”] → 第一版保留用户自由度，通过已有名称建议减少重复；全局归一化和标签模板留作后续变更。
- [Prompt 指导包含类似指令的文本] → 当前不执行 Prompt；未来构建器必须把它作为受限用户数据，不允许覆盖系统规则。
- [主播列表批量加载标签增加 repository 复杂度] → 使用一次批量查询和分组辅助函数，并覆盖空列表、大量主播及稳定排序测试。
- [整组替换标签可能丢失并发编辑] → 当前客户端是单用户本地应用；command 返回最新 DTO，未来如引入多窗口并发编辑再增加版本号或乐观锁。
- [身份合并时标签超过上限] → 目标优先、来源按顺序截断，并发布不含标签原文的可诊断提示。
- [与 ASR 变更的 migration 编号冲突] → 实施前以当前主分支最新 migration 为准，不修改另一活动变更文件。

## Migration Plan

1. 在当前数据库版本基础上新增 `streamer_tags` 表、唯一索引和级联外键；已有主播不插入占位标签。
2. 扩展领域模型和 repository，保证所有主播 DTO 返回 `tags: []` 或有序标签。
3. 将标签写入接入创建、编辑、归档恢复和身份合并事务。
4. 更新 Tauri command、React 表单、标签展示和浏览器演示状态。
5. 增加迁移幂等、事务回滚、标签校验、合并、worker 不重启、DTO 序列化和 UI 测试。
6. 回滚应用代码时保留标签表和数据；旧版本忽略该表，不影响主播、监听、录制和视频关系。

## Open Questions

本次范围和行为均已确认。全局标签模板、自动标签生成、标签筛选、AI 项目快照、Prompt 构建、精彩提取和自动切片分别留给后续变更。
