## Context

客户端当前把已完成 MKV 分片登记到 SQLite，并在监控中心和视频库中通过 `open_video` 调用系统默认播放器。Tauri 2.0 前端运行于平台 WebView；macOS 的 WKWebView 不能可靠播放 Matroska 容器，即使开放本地文件协议也无法保证 MKV 解封装和编解码支持。

项目已经依赖用户配置的 FFmpeg/FFprobe，并以 MKV 无转码分片作为可恢复录制源。预览功能必须保持该录制路径不变，不能让格式转换延迟分片登记、阻塞监听任务或改变 ASR 的输入。录像目录可由用户指定，因此媒体访问权限还需要避免向 WebView 暴露任意本地目录。

## Goals / Non-Goals

**Goals:**

- 在本次监听视频和历史视频库中预览单个已完成分片。
- 对 MP4 直接播放，对 MKV 按需生成适合 WebView 的 MP4 缓存。
- 优先无损重封装，仅在编码不兼容时回退为 H.264 + AAC 转码。
- 提供可去重、可观察、不会无限并发的后台预览任务。
- 提供有容量上限、可过期、与录像业务数据隔离的缓存生命周期。
- 保留系统播放器打开、文件管理器定位和原始文件删除能力。
- 以 macOS 为首期验收平台，同时保持 Rust 服务和 FFmpeg 计划可迁移。

**Non-Goals:**

- 不合并同一录制会话的多个分片，不提供整场统一时间轴或无缝连播。
- 不预览正在写入的 partial 文件，也不尝试读取未登记文件。
- 不为预览修改、替换或自动删除原始 MKV。
- 不实现字幕、画中画、逐帧操作、缩略图生成或播放列表。
- 不改变 ASR、NLP、高光识别和正式剪辑导出的输入或产物。
- 不在本次变更中打包 FFmpeg sidecar，继续使用现有路径设置和环境诊断。

## Decisions

### 1. 使用按需 MP4 预览缓存，而不是直接播放 MKV

Rust 侧新增独立 `PreviewService`。前端请求预览后，服务先根据视频记录和文件状态判断是否可用：MP4 源文件可直接返回；MKV 则检查缓存，未命中时创建后台准备任务。准备完成后，前端使用统一播放器弹窗中的 HTML `<video>` 播放。

选择该方案是因为 MP4 在 WKWebView/WebView2 中的兼容性明显优于 MKV，并且按需生成不会让每次录制结束都产生额外磁盘写入。备选方案是集成 mpv/libVLC 原生播放器；它能直接播放 MKV，但会增加二进制体积、许可证审查、原生窗口嵌入和多平台发布成本，因此暂不采用。另一个备选方案是让 WebView 直接读取 MKV；该方案无法满足 macOS 稳定预览要求，因此不采用。

### 2. 重封装优先，必要时自动转码

预览工作器首先执行只映射第一路视频和可选第一路音频的 MP4 重封装计划，复制现有编解码数据并写入 `faststart` 元数据。重封装完成后还必须通过编解码兼容校验；即使 FFmpeg 成功写出 MP4，只要结果不是 H.264 视频和可选 AAC 音频，服务仍自动执行转码。转码器按平台硬件编码器、软件编码器顺序尝试；编码器虽然出现在列表中但运行失败时继续尝试下一个，全部不可用后才返回可操作错误。

所有计划都复用设置中的 FFmpeg/FFprobe 路径，并通过参数数组启动子进程，不拼接 shell 命令。使用 FFprobe 读取时长和轨道信息；FFmpeg 使用 `-progress pipe:1` 输出进度。无法得到可靠时长时仍允许转换，但前端只显示不确定进度。

不在录制结束时自动转换全部分片，因为大量无人查看的录像会重复占用磁盘和 CPU。正式高光切片或导出仍应在对应工作流中生成正式 MP4，而不是复用可清理的预览缓存。

### 3. 单工作器队列、任务去重和后台完成

`PreviewService` 使用一个全局 semaphore，任何时刻最多运行一个重封装或转码进程。请求以缓存键去重；相同源版本的重复点击共享同一任务，不重复启动 FFmpeg。不同视频依次排队，避免与最多四路并发录制争抢过多 CPU 和磁盘吞吐。

任务状态至少包含 `queued`、`probing`、`remuxing`、`transcoding`、`ready` 和 `failed`。Tauri command 返回预览请求标识和当前快照，后端通过事件推送后续状态；前端也可查询状态，以覆盖窗口隐藏、页面重建或事件错过的情况。关闭播放器不会取消任务，任务在后台完成并保留缓存。应用显式退出时停止预览子进程，残留临时文件由下次启动清理。

### 4. 缓存采用内容指纹、sidecar 清单和原子发布

缓存目录固定为 Tauri `app_cache_dir()/video-preview/`。缓存键使用规范化源路径、文件大小、修改时间和预览配置版本的 SHA-256；源文件发生变化或转换配置升级时会得到新键。每个 MP4 配套一个 JSON sidecar，记录视频 ID、源指纹、创建时间、最后访问时间、生成方式和格式信息；这些数据不写入 `videos` 主业务表。

FFmpeg 只写入 `.part` 临时文件，成功退出且 FFprobe 验证输出包含可播放视频轨后才原子重命名为最终 MP4。缓存命中会更新最后访问时间。启动应用和创建新任务前执行清理：删除遗留临时文件、删除超过 7 天未访问的条目，并按最久未使用顺序把总量压到 10 GB 以下；正在播放或生成的条目不参与当次清理。

外部移动或删除源文件时，如果该视频已有有效缓存，则允许继续预览，同时保持源文件“缺失”状态；没有缓存时返回缺失错误。用户在应用内成功删除视频或会话后，对应缓存也进入清理，避免用户已删除内容仍长期保留副本。

### 5. 受限本地媒体访问

生成的缓存只通过 Tauri asset protocol 暴露，静态 scope 限定到应用预览缓存目录。对于数据库中已经是 MP4 的源文件，Rust 在校验记录、文件类型和存在性后，只把该精确文件加入运行时 asset scope，不开放整个用户录像目录。前端使用 `convertFileSrc` 生成媒体 URL，禁止接受前端传入的任意本地路径。

播放器只消费后端返回的预览描述，不自行拼接文件 URL。媒体响应必须支持范围读取，以保证进度拖动。播放器关闭时释放媒体元素和 URL 引用，但不删除缓存。

### 6. 前端共用一个播放器状态机

监控中心的本次分片和视频库卡片共用 `VideoPreviewDialog`。点击“预览”后立即打开弹窗并显示排队或转换状态；缓存准备好后自动设置媒体源并尝试播放。若 WebView 的自动播放策略阻止播放，则停留在可播放状态并展示明确播放按钮。

播放器提供播放/暂停、进度拖动、当前时间/总时长、音量、倍速和全屏。错误面板提供“重试”和“使用系统播放器打开”；系统打开与文件管理器定位继续调用现有 command。缺失源文件但缓存有效时允许预览，系统打开和定位仍保持禁用或返回缺失提示。

### 7. 磁盘和错误保护

创建任务前，服务先清理过期缓存，再检查缓存卷可用空间。需要的最低空间按预计输出大小加 2 GB 安全余量计算；无法满足时不启动 FFmpeg，并提示用户清理缓存或磁盘。运行中遇到磁盘写满、FFmpeg 缺失、探测失败、损坏媒体、无视频轨或转码器不可用时，任务进入 `failed`，保留原始录像并删除未发布临时文件。

失败不会无限自动重试。用户可以显式重试；同一缓存键的新重试会创建新任务快照。错误返回中文摘要和稳定错误码，日志可记录脱敏后的诊断信息，但不把任意本地文件内容或直播签名 URL发送到网络。

## Risks / Trade-offs

- [回退转码可能占用大量 CPU] → 全局限制为一个预览任务，并优先重封装；录制链路不等待预览任务。
- [预览缓存接近原文件大小] → 使用 7 天过期、10 GB 上限、LRU 清理和转换前空间检查。
- [FFmpeg 构建缺少可用 H.264 编码器] → 启动任务前探测编码器，保留系统播放器入口并返回安装或配置提示。
- [asset protocol 配置过宽会暴露本地文件] → 只静态开放预览缓存目录，对源 MP4 逐文件动态授权，所有请求从数据库视频 ID 开始校验。
- [事件可能在窗口隐藏时丢失] → command 返回状态快照，并提供状态查询以恢复播放器状态。
- [应用退出或崩溃留下半成品] → 使用 `.part` 文件、成功后原子发布，并在启动时清理遗留临时文件。
- [硬件编码器在不同设备表现不一致] → 探测后使用，失败时尝试软件编码器；命令计划和输出校验由独立测试覆盖。

## Migration Plan

1. 增加预览领域模型、FFmpeg 计划和独立 `PreviewService`，不修改现有录像表结构。
2. 注册预览 command、状态事件和受限 asset protocol scope，同时保留现有 `open_video`。
3. 增加播放器弹窗，并把监控中心和视频库的主要播放操作切换为“预览”；系统打开作为次要操作保留。
4. 在 macOS 上用重封装、转码、无音轨、损坏文件、中文路径、大文件和重复请求样本验收。
5. 若发布后需要回滚，只移除预览入口和服务注册；原始录像、SQLite 数据和现有系统打开能力不需要迁移或恢复。

## Open Questions

本次立项没有阻塞实施的开放问题。整场连续播放、缓存设置界面、FFmpeg sidecar 打包及 Windows/Linux 实机验收分别作为后续变更处理。
