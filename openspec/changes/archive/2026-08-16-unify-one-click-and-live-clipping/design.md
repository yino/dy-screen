## Context

当前客户端已经分别具备 AI 项目、本地 ASR、高光 Agent、候选选择、剪辑工程、字幕纠错、转场素材匹配和显式 MP4 导出能力，但这些能力由不同页面和独立运行记录驱动。普通 AI 项目在开始时冻结输入，一个高光运行对应一个项目，一个剪辑工程又通过唯一 `highlight_run_id` 绑定一个高光运行；该模型适合人工逐步处理，却无法安全表达“用户授权一次后自动推进”或“同一场直播不断出现已完成分片、最终汇总为一个合辑”的生命周期。

直播录制由独立 recorder 管理，活动文件可能仍在写入。智能成片不能降低录制可靠性，也不能把可变文件追加进已经冻结的 AI 项目。因此，智能直播必须只消费 recorder 已封装、已登记并可通过源指纹校验的不可变分片，并把每个新增分片作为独立批次处理。

本变更涉及 Tauri/Rust 编排、SQLite 数据模型、后台事件、AI 工作区和剪辑工程版本，且要同时兼容普通手动流程、历史项目以及 macOS arm64、macOS Intel x86_64 和 Windows x64。直播素材还包含两种不同生命周期：已结束回放是创建时即可冻结完整来源的有限任务，正在直播则是持续追加完成分片的增量任务。LLM 继续只接收必要文本；视频、音频、路径、凭据和 Provider 原始响应不得进入请求、事件或遥测。

## Goals / Non-Goals

**Goals:**

- 提供一个 Rust 拥有的 `SmartClippingWorkflow`，用统一状态机表达本地视频、直播回放和正在直播三种执行模式。
- 用户只需在本地任务、回放任务或直播场次开始时授权一次，流水线即可自动推进至可审阅草稿；导出仍由用户明确选择目标并触发。
- 本地和直播回放模式冻结一次输入；正在直播模式只对新增的完整分片创建不可变批次，且任何 AI 失败、取消或恢复都不影响录制。
- 复用现有 ASR、高光、字幕纠错、转场匹配、剪辑审阅和 FFmpeg 导出服务，保持普通项目的手动门禁不变。
- 让一个直播合辑草稿可安全引用多个 AI 项目和高光运行，并支持跨分片合并、去重、草稿代次、人工编辑保护与导出冻结。
- 持久化输入指纹、阶段尝试和结果代次，使失败阶段可重试、应用重启后可恢复、迟到事件不可污染当前状态。
- 采集不含业务正文和本地标识的漏斗、耗时和终态指标；把相关高光结束后 10 分钟内出现首个可审阅直播草稿作为时效目标。

**Non-Goals:**

- 自动发布、静默导出、无人审阅成片或修改已经导出的 MP4。
- 读取正在写入的录像、流式 ASR、直接处理直播流或让 AI 失败停止录制。
- 上传视频或音频、支持任意直播 URL、绕过登录、验证码、DRM、付费内容或私有直播间控制。
- 从抖音或其他平台获取历史回放、接受平台回放 URL，或把仍在录制的会话伪装为冻结回放。
- 新建整片模板市场；“匹配模板”仅复用现有转场/动画素材目录及其冻结阈值。
- 自动生成 BGM、封面、发布文案，或支持移动端、Web、Linux。

## Decisions

### 1. 使用父工作流和不可变子批次，而不是扩展可变 AI 项目

新增 Rust 领域对象 `SmartClippingWorkflow`。父任务保存模式、受信来源、授权快照、配置指纹、当前状态、活动草稿代次和可选直播游标；`SmartClippingBatch` 保存一个冻结输入集合及其普通 AI 项目和高光运行关联。领域层使用三个显式模式：`local`、`replay` 和 `live`；保留已有 `live` 序列化值表示正在直播，避免既有任务被重新解释。

- 本地模式在创建时生成一个批次，冻结用户通过系统选择器确认的视频。
- 回放模式绑定系统已登记、已结束且非空的录制会话，按 `started_at ASC, id ASC` 将全部合法分片冻结到一个有限批次；任务保存 `recording_session` 身份和冻结集合指纹，目录后续变化不得静默扩展该任务。
- 正在直播模式绑定系统已监听且正在录制的会话。recorder 完成封装并登记分片后，编排器按 `(session_id, video_id, source_fingerprint)` 幂等创建批次；同一分片不得重复处理。
- 批次继续使用普通 AI 项目、ASR 和高光服务，不向这些服务传递正在增长的输入集合。

回放不直接降格为无来源的本地文件任务，因为那会丢失主播、场次、分片顺序、重复任务判断和审计关系。替代方案是向同一 AI 项目持续追加正在直播分片，但这会破坏输入冻结、缓存指纹、全局 ASR 队列和运行恢复语义，因此不采用。另一方案是为智能成片复制整套 ASR/高光实现，会形成两套质量和安全边界，也不采用。

### 2. 一次授权形成有界能力令牌

创建任务时由用户一次确认来源、成片目标、输出偏好、Provider、将发送的文本类型和最小必要范围。Rust 持久化授权时间、作用域、Provider/模型标识和授权摘要，不保存 Key、完整 Prompt 或正文。授权仅对当前本地任务、当前回放冻结集合或当前直播会话有效，不可跨任务复用。

编排器只有在客户端激活有效、Provider 已配置、资源诊断通过且授权作用域匹配时，才可自动启动高光、纠错和转场阶段。应用重启后先重新验证激活和 Provider 可用性，再恢复待执行阶段；不得仅因进程启动重发 LLM 请求。普通 AI 项目继续逐阶段显式授权。

替代方案是每个阶段重复弹窗，这不能解决功能分散问题；全局永久授权又超出用户可理解范围，因此采用任务级或场次级授权。

### 3. Rust 状态机拥有编排，子服务保持单一职责

建议新增 `src-tauri/src/ai/smart_workflow.rs`，由它调用既有 command service 之下的领域服务，而不是从 WebView 串联多个 command。阶段顺序为：

1. 输入预检与冻结；
2. 本地 ASR；
3. 高光发现、全局评分和候选发布；
4. 按既有合格/优秀冻结阈值更新候选账本，优秀候选自动入选；
5. 创建或更新合辑草稿及工程字幕副本；
6. 对仍等于 ASR 原文且未隐藏的工程字幕执行保守纠错；
7. 对未人工锁定边界执行现有两阶段转场匹配；
8. 发布可审阅状态，等待用户编辑或显式导出。

每个阶段写入 `input_fingerprint`、`attempt_generation`、状态、进度、结果引用和脱敏错误。只有成功结果与当前指纹一致时才可复用；重试从失败阶段开始，不重做无变化的成功前置阶段。取消父任务会停止其待执行或运行中的 AI 子任务，但不会取消 recorder。

替代方案是由 React 根据事件逐步调用后端。这会在页面卸载、刷新和应用重启后丢失所有权，并产生重复调用竞态，因此编排必须位于 Rust。

### 4. 用候选账本跨批次合并，而不是把模型结果直接拼接

父工作流维护候选账本。每条账本记录关联原始候选、批次、直播会话、视频 ID、稳定句段 ID 和规范化会话时间范围。批次高光仍遵循 15–90 秒、不可跨源文件的既有校验；跨分片上下文只把前一完整分片末尾的有限句段作为只读上下文，最终候选必须映射到真实、已完成的一个或多个来源区间。

合并采用确定性规则：核心稳定句段相同，或规范化时间区间高度重叠且语义指纹相同的候选归为一组；保留最高分版本，并保存被合并来源以便审计。对确实跨分片的高光，账本可以形成一个逻辑候选和多个连续来源区间，剪辑工程仍按各源文件拆成连续工程片段。低于合格阈值的候选保留审计但不进入默认审阅；达到优秀阈值的候选自动进入活动草稿。

替代方案是直接拼接每批全部优秀候选，容易重复同一段内容；让 LLM 对整场直播反复全量复评则成本和延迟随直播时长增长，因此不采用。

### 5. 泛化剪辑工程来源关系以支持多运行合辑

现有 `ai_clip_projects.highlight_run_id UNIQUE NOT NULL` 和多处“候选必须属于该运行”的校验无法表达直播合辑。迁移将：

- 重建 `ai_clip_projects`，保留 `highlight_run_id` 作为兼容的主来源，去除全局唯一约束，并增加可空 `smart_workflow_id`、`draft_generation` 和自动化所有权状态；
- 新增 `ai_clip_project_sources(clip_project_id, highlight_run_id, workflow_batch_id, source_order)`，为所有历史工程回填原 `highlight_run_id`；
- 通过部分唯一索引继续保证非智能工程对一个高光运行只有一个默认工程；
- 将片段追加、字幕复制、预览、转场和导出校验改为验证候选所属运行存在于工程来源关联，而不是只等于主来源；
- 为跨分片逻辑候选保存到账本和工程片段的映射，原始 `candidate_id`、`input_id` 和 ASR 引用仍保持可追溯。

智能草稿并不是把多个子工程渲染后再拼接；它是一个复用现有编辑器和导出器的真正合辑工程。这样用户能在同一时间轴审阅、纠错、调整转场并一次导出。

替代方案是先为每个批次生成独立 MP4 再二次合并，但会丢失工程级字幕、边界、人工编辑和无损重试语义。仅把第一个高光运行伪装成全部来源则会绕过后端来源校验，也不采用。

### 6. 活动草稿采用代次和所有权保护

一个智能任务同一时间只有一个自动化可写的活动草稿代次。更新前，编排器在事务中比较工作流代次、工程版本和自动化所有权：

- 尚未人工编辑、未导出且未进入导出的草稿可由新增优秀候选确定性更新；
- 用户首次进行片段、字幕、动画、转场或输出规格修改后，当前工程转为用户拥有，自动化不得覆盖；后续高光创建下一代草稿，并可从已冻结选择偏好派生但不能写回人工工程；
- 用户显式开始导出时冻结工程版本、来源集合和草稿代次。导出期间禁止任何自动化或人工结构修改；成功、失败或取消均保留该冻结快照的审计；
- 导出后到达的新高光只进入下一代草稿，不修改已导出文件或旧工程。

替代方案是始终向同一个工程追加片段，会覆盖用户审阅成果并造成导出竞态；直播结束后才一次性出草稿又无法满足边播边剪的时效目标。

### 7. 通过持久化命令快照和类型化事件恢复 UI

SQLite 新增以下逻辑实体，具体列名在实现时按现有 repository 风格确定：

- `ai_smart_workflows`：父任务、模式、来源、授权摘要、配置指纹、状态、活动代次和直播游标；
- `ai_smart_workflow_batches`：冻结输入、源指纹、普通 AI 项目/高光运行引用和批次状态；
- `ai_smart_stage_attempts`：阶段、输入指纹、尝试代次、状态、结果引用、耗时和脱敏错误；
- `ai_smart_candidates` 与来源映射：跨批次候选账本、合并组和真实来源区间；
- `ai_smart_drafts`：草稿代次、剪辑工程、所有权、冻结版本及导出关联；
- `ai_clip_project_sources`：剪辑工程允许引用的高光运行集合。

Rust 发布带 `workflow_id`、`workflow_generation`、`batch_id`、`stage` 和单调序号的 `ai-smart-workflow-event`。事件只用于及时刷新；页面挂载、重连和应用启动后必须通过查询 command 获取完整快照。repository 忽略旧代次或旧序号事件。

替代方案是只靠内存和事件维护进度，无法保证重启恢复和迟到事件隔离。

### 8. 两种直播任务使用不同进度和收敛语义

回放任务在创建时知道固定分片总数，以 `processed_batches / total_batches` 和总体阶段表示进度；全部冻结分片到达终态后收敛，不等待目录刷新或新分片。正在直播任务不知道最终输入总量，以完成分片游标、当前批次、积压数和来源延迟表示进度；直播结束后先消费游标内全部完成分片再收敛。若同一会话已经存在活动或已完成的智能任务，新建任务必须显式确认，不得因会话从活动转为结束自动创建第二个回放任务。

前端把“本地视频”和“直播素材”作为一级来源选择，并在“直播素材”中用分段控件展示“正在直播”和“直播回放”。两类列表分别查询，主播当前正在直播不得隐藏其已结束回放。回放项明确标注“本机已完成录制”，不展示平台回放 URL 输入或下载暗示。

替代方案是让“直播间”只展示活动会话并把历史回放留在高级模式，但这继续暴露原有功能分散问题；把活动和历史会话混在同一列表又会隐藏两种完全不同的进度与授权语义，因此不采用。

### 9. 直播调度受资源和时效目标约束

智能批次复用全局单并发 ASR 队列，不抢占用户明确立即切换的任务。高光、纠错和转场调用使用现有有界 Provider 并发和重试策略。若直播分片到达速度超过处理速度，系统展示积压数量和预计延迟，按源时间稳定处理，不丢弃已登记分片。

“10 分钟”从构成高光的最后一个来源分片完成登记时开始，至包含该高光的草稿首次进入可审阅状态结束。该目标只用于正在直播增量任务；回放任务记录固定总数、完成比例和从授权到首稿的桶化耗时，不套用增量延迟口径。指标作为服务目标而非通过读取未完成文件来强行保证。交付顺序为本地模式、回放冻结模式、正在直播增量模式。

### 10. 遥测仅记录脱敏漏斗和延迟

允许记录模式、平台、阶段、终态、桶化耗时、批次数、候选数、自动入选数、人工采用数、首稿延迟和导出终态。任务 ID 在上报前使用会话级不可逆标识或仅做聚合。不得记录媒体或字幕正文、候选理由、主播名称、直播间 ID、本地路径、Prompt、Key、Provider 原始响应或可还原用户内容的指纹。

## Risks / Trade-offs

- [跨运行剪辑工程迁移影响既有查询和唯一约束] → 先回填来源关联并为普通工程建立部分唯一索引；增加迁移、回滚兼容和历史工程回归测试，所有来源校验集中到 repository API。
- [直播处理速度低于分片产生速度] → 保持有界队列和稳定游标，展示积压与延迟，不读取活动文件、不抢占录制资源；用首稿延迟指标定位瓶颈。
- [跨分片候选重复或边界不完整] → 使用稳定句段、真实时间区间和语义指纹的确定性账本；模型输出不能绕过本地映射校验，审阅界面保留来源。
- [自动更新覆盖用户编辑] → 事务比较所有权、工程版本和草稿代次；任何人工 mutation 都永久关闭该代次的自动写权限。
- [重启后重复产生 Provider 费用] → 阶段成功结果按输入指纹复用；非终态尝试标记中断，重新验证激活和授权后创建新尝试代次，旧响应不可提交。
- [一次授权范围过宽] → 授权只覆盖当前任务或直播场次，展示必要文本范围和 Provider；来源、Provider 或目标配置改变时要求重新授权。
- [AI 阶段故障影响 recorder] → recorder 不由智能工作流持有取消令牌；只订阅已完成分片事件，所有失败均收敛到任务/批次状态。
- [回放与正在直播状态竞态] → 创建命令在同一读事务内重新校验会话结束状态、非空分片集合和活动 worker；模式不匹配时拒绝整个任务，不创建部分记录。
- [同一会话重复创建任务] → 保存来源会话和冻结集合指纹，列表展示已有任务；重复创建必须由用户明确触发，事件重放和会话结束不得自动复制任务。
- [自动转场素材未下载导致草稿不可导出] → 草稿可先审阅，但显式标记素材准备状态；既有导出门禁继续阻止缺失或校验失败素材。
- [多平台 sidecar 行为差异] → 在 macOS arm64、macOS Intel x86_64、Windows x64 分别验证资源诊断、ASR、FFmpeg 预览和导出；不以开发机系统二进制替代随包资源。

## Migration Plan

1. 在功能关闭状态下增加智能工作流表和索引；重建 `ai_clip_projects` 来源约束，为历史工程回填 `ai_clip_project_sources`，校验每个旧工程恰有一个来源。
2. 修改剪辑 repository 的候选归属查询，使普通工程行为保持不变，并通过迁移和历史工程回归测试后再接入编排器。
3. 实现父状态机、阶段尝试、事件快照和本地单批模式，先发布本地“一键剪辑”。
4. 增加 `replay` 模式和已结束会话冻结校验，复用本地单批编排并保留场次来源，在回放完整性、重复创建和恢复测试通过后启用直播回放。
5. 接入完成分片事件、跨批次候选账本和草稿代次，完成积压、恢复、人工编辑和导出竞态测试后启用正在直播模式。
6. 按平台验证资源、安装包和三种模式端到端流程，并观察脱敏漏斗、失败分类及首稿延迟。

回滚时先关闭智能成片入口和新批次消费，等待当前阶段收敛或将其标记暂停；普通 AI 项目和历史工程继续读取回填后的兼容字段。不得删除智能任务、来源关联、草稿或已经导出的文件。旧版本若不理解智能合辑，应隐藏带 `smart_workflow_id` 的工程，而不是把它误当成单运行默认工程。

## Open Questions
