## Context

当前 `ApiClient` 使用 `PlainJsonCodec` 调用授权运营服务端，`ActivationService::activate` 收到激活成功响应后立即把本地状态标记为 `active`，Tauri command 随即恢复 Supervisor 和 AI runtime；独立心跳任务约一秒后才验证 `device_id`、`activate_code` 请求头和设备绑定状态。因此代理丢弃下划线请求头时，用户会短暂进入首页，再被 `1001` 心跳结果锁回激活页。

后端 Wiki 明确：前台接口 HTTP 恒为 200，以 `{ code, data, msg }` 判断结果；激活凭据位于请求体，心跳凭据位于 `device_id`、`activate_code` 请求头；强制下线使用 `code=201` 及 `revoked/state/reason`。生产信封协议虽然是后端最终契约，但用户已决定本期继续使用兼容期明文 JSON，不实现加密或签名。本次还必须满足桌面客户端可诊断性，同时不能把完整设备号、激活码、令牌或响应正文写入控制台。

现有工作区已有尚未提交的激活门禁和请求头兼容修改。实施时必须在这些修改之上增量完成，不得回退访问验证通知去重或转场素材同步等相邻用户改动。

## Goals / Non-Goals

**Goals:**

- 只有激活接口与紧随其后的心跳都确认有效时，才向前端发布 `active` 并恢复授权依赖任务。
- 完整覆盖卡密、设备、强制下线、请求头契约、暂时服务故障和预留协议错误的处置矩阵。
- 统一发送权威下划线请求头与兼容连字符别名，并输出足以定位代理问题的脱敏结构化日志。
- 将长期授权秘密从 SQLite 迁移到 macOS Keychain 或 Windows Credential Manager；数据库只保存非秘密状态摘要。
- 保持激活门禁不可绕过，消除首页闪现和后台任务提前启动。

**Non-Goals:**

- 不实现信封加密、ChaCha20-Poly1305、HKDF、Ed25519、设备签名公钥、`encKey` 保存或轮换。
- 不修改服务端 API 字段、业务码或卡密状态机。
- 不通过请求体、查询参数或其他旁路重复传送心跳凭据来绕过代理配置。
- 不输出完整激活码、设备 ID、token、Cookie、请求签名、响应正文或本地敏感路径。
- 不处理直播平台登录、验证码自动化或其他访问控制绕过。

## Decisions

### 激活采用同步两阶段确认

`ActivationService::activate` 先调用 `/client/activate`，校验成功响应并暂存凭据，然后在同一次 command 内立即调用 `/client/heartbeat`。本地状态在此期间为 `verifying`，`active=false`；只有心跳返回 `code=200`、`revoked=false`、`state=ACTIVE` 时才原子发布有效授权、恢复 Supervisor/AI runtime 并向前端返回成功。

激活响应成功但心跳失败时不挂载主界面。确定的授权错误进入重新激活状态；暂时错误保留在激活页并允许重试，前端输入在请求失败后不清空。选择同步确认而不是继续依赖后台首个心跳，是因为前者能在唯一解锁点验证完整请求头和设备绑定契约，彻底消除首页闪现。后台周期心跳仍负责后续续约。

服务用单次激活代次和单飞锁串行化激活/心跳状态写入，旧请求完成后不得覆盖新一次激活或清除状态。恢复后台任务仍由 Tauri command 在收到最终 `active` 结果后执行，`ActivationService` 不直接依赖 Supervisor。

### 使用显式错误处置矩阵

统一 API 错误保留业务码、稳定分类、脱敏消息和请求关联 ID，授权服务按以下规则处理：

| 结果 | 授权状态 | 行为 |
|---|---|---|
| `code=200`、`revoked=false`、`state=ACTIVE` | `active` | 更新令牌、有效期、服务端时间并保持运行 |
| `code=201`、`revoked=true` 或 `state!=ACTIVE` | `revoked` | 清理令牌、暂停任务、要求重新输入激活码 |
| `1002~1006`、`2003~2004` | `invalid`/`revoked` | 视为确定的卡密或设备失效并重新激活 |
| `1001`、`2001` | `contract_error` | 锁定激活页，提示请求头/代理契约异常并要求重新激活，不误报普通卡密失效 |
| `1007`、`9000`、网络、超时、无效响应 | `retrying` | 不清除仍在宽限期内的凭据，按有界退避或用户操作重试 |
| `9104`、`9105` | `retrying` | 使用现有服务端时间偏移或当前明文会话立即重试一次；重复失败后重新激活 |
| `9101~9103` | `retrying` 后 `invalid` | 有界重试一次，仍失败则重新激活 |

心跳的 `1001/2001` 仍然锁定全部主功能，满足授权异常必须重新激活的要求；但提示同时指出客户端已发送哪些规范头及代理部署要求。`9000` 和网络故障不等价于卡密失效，否则服务端短暂故障会让所有客户端丢失本地授权。

### 集中构造请求头并保留兼容别名

所有需授权请求继续通过 `client_headers` 构造请求头，同时发送：

- 权威契约：`device_id`、`activate_code`
- 兼容别名：`device-id`、`activate-code`

客户端不会把凭据复制到心跳正文或 URL。服务端或反向代理必须启用 `underscores_in_headers on;`，或者后端鉴权中间件显式读取连字符别名。日志只记录四个头各自的 `present=true/false` 和设备末尾提示，绝不记录值。

### 在统一 API 边界输出结构化脱敏诊断

`ApiClient` 为激活和心跳默认输出 JSONL 请求开始与完成/失败事件。请求摘要包含组件、事件、方法、路径、阶段、参数字段名、凭据是否存在、平台和客户端版本；响应摘要包含耗时、HTTP 状态、业务码、`revoked/state/reason`、`x-request-id`、`x-trace-id` 和稳定错误分类。其他客户端 API 只在失败时输出同结构摘要，避免正常日志噪声。

日志序列化使用专用诊断 DTO和字段白名单，不对原始 `serde_json::Value`、`HeaderMap` 或响应正文执行通用 Debug。设备只允许复用 `device_id_hint`；激活码、token、未来 `encKey` 和完整 URL 均没有可序列化日志字段。响应 `msg` 只映射到内部错误分类和面向用户的安全文案，不原样打印。关联头在解析正文前读取，因此无效响应也能用于服务端排查。

### 使用可替换的系统凭据存储边界

新增 `ActivationSecretStore` trait，生产实现使用 macOS Keychain/Windows Credential Manager，测试使用内存 fake。安全存储保存完整 `device_id`、`activate_code` 和离线 token；SQLite 保存 `device_id_hint`、状态、`expire_at`、`grace_sec`、时间偏移、策略开关、心跳时间和脱敏错误。由于本期不启用信封协议，不生成设备签名私钥，也不保存服务端返回但未使用的 `encKey`。

数据库升级时先读取旧 `client_activation` 单行记录，再把秘密写入系统凭据存储并回读确认，最后以事务迁移到不含秘密列的新表。任一步失败时保留旧表且不报告迁移完成，应用保持激活门禁并提供安全错误；不得先删除明文再尝试写 Keychain。成功迁移后清除旧秘密字段，后续重新激活覆盖同一个凭据项。清除授权时同时删除系统凭据和 SQLite 元数据，任一侧失败均保持门禁并允许幂等重试。

### 前端使用独占门禁状态机

`ActivationStatus` 增加 `verifying` 和 `contract_error`，删除已经失效的开发免激活分支。只要 `activation.active !== true`，React 只渲染独占激活页，不挂载 Sidebar、监控、视频库或 AI 工作区。提交后按钮进入“正在验证”，在同步心跳完成前不显示首页；确定错误要求重新输入，暂时错误保留用户输入并提供重试。

## Risks / Trade-offs

- [Nginx 继续丢弃下划线请求头] → 客户端无法单方面满足严格后端契约；通过双头兼容、`contract_error` 和请求关联日志明确外部部署修复点，不使用不受支持的正文旁路。
- [系统凭据存储不可用或被用户拒绝] → 保持激活门禁并显示安全存储错误，不回退 SQLite 明文；提供测试 fake 和平台诊断。
- [旧明文记录迁移中断] → 采用“先写安全存储、回读验证、后迁移 SQLite”的顺序，启动时幂等恢复，不删除唯一可用凭据。
- [激活后同步心跳增加一次等待] → 激活只多一次有界网络请求，但能在解锁前验证真实授权链路；界面展示明确进度并禁止重复提交。
- [默认控制台日志增加输出] → 仅激活/心跳记录成功摘要，其他接口只记录失败；专用 DTO、白名单和泄密测试限制输出。
- [明文 JSON 仍传输敏感数据] → 正式 API 地址必须使用 HTTPS；本期明确接受后端兼容期明文，后续信封协议需独立 OpenSpec。

## Migration Plan

1. 先增加错误分类、诊断 DTO、关联头解析和测试，不改变现有授权状态行为。
2. 引入 `ActivationSecretStore` 及平台实现，增加旧 SQLite 凭据的幂等迁移和回滚测试。
3. 将激活 command 改为“激活响应 + 同步心跳”两阶段确认，并接入单飞/代次保护。
4. 更新周期心跳错误矩阵、后台暂停恢复和前端独占门禁状态。
5. 在本地 mock 服务覆盖所有业务码，再对配置正确的开发服务端执行真实激活与心跳验收；通过 `x-request-id`/`x-trace-id` 关联客户端和后端日志。
6. 部署前确认正式地址为 HTTPS，Nginx 已启用下划线请求头或后端支持连字符别名。

回滚客户端版本不会重新写入已清除的 SQLite 明文秘密；用户可能需要在旧版本重新输入激活码。数据库迁移保留非秘密授权元数据，录像、主播、项目和素材数据不受影响。
