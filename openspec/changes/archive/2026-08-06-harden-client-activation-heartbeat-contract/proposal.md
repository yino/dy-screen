## Why

客户端当前在激活接口成功后会先进入主界面，再由后台心跳确认授权；当代理丢弃 `activate_code` 等下划线请求头时，心跳返回 `1001`，客户端随即重新锁回激活页，形成闪屏和无法定位根因的重复激活。现有实现还没有完整覆盖后端 Wiki 定义的错误码、请求关联头和安全诊断要求，需要统一激活、心跳、门禁和日志契约。

## What Changes

- 激活接口成功后立即执行一次同步心跳，只有心跳返回 `code=200`、`revoked=false` 且 `state=ACTIVE` 才发布激活成功、恢复后台任务并进入主界面。
- 统一激活与心跳错误分类：确定的卡密或设备失效强制回到激活门禁；网络、超时、服务端内部错误和激活并发错误进入可重试状态；时钟偏差和密钥失步保留明确恢复分类，为未来协议升级预留边界。
- 心跳同时发送后端契约要求的 `device_id`、`activate_code` 和兼容代理的 `device-id`、`activate-code`，并为代理丢失请求头返回专门的部署诊断，不将其误报为普通卡密无效。
- 在统一 Rust API 客户端增加结构化控制台诊断，记录请求方法、路径、阶段、耗时、HTTP 状态、业务码、授权状态、请求关联 ID及请求头是否存在；所有激活码、令牌、设备完整标识和原始响应正文必须脱敏或省略。
- 将激活码等长期敏感凭据迁移到操作系统安全凭据存储；SQLite 只保存授权状态、脱敏设备提示、有效期、心跳时间和安全错误摘要，并兼容迁移既有明文记录。
- 更新激活门禁交互，消除“进入首页后又返回”的中间状态，并分别展示卡密失效、设备绑定异常、请求头契约异常和暂时网络故障。
- 本期继续使用后端当前兼容的明文 JSON 请求与响应，不实现信封加密、Ed25519 请求签名、`encKey` 轮换或加密正文。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `client-activation-service`: 完善激活后的同步心跳确认、请求头兼容、错误码分级、安全凭据存储和脱敏 API 控制台诊断。
- `desktop-client-shell`: 在服务端完整确认授权前持续锁定主界面，并针对不同授权与部署异常展示稳定、不可绕过的激活门禁。

## Impact

- Rust：修改 `src-tauri/src/api.rs`、`activation.rs`、`app.rs` 和授权 SQLite repository，引入 macOS/Windows 可用的系统凭据存储适配层。
- React：修改激活状态 DTO、激活页状态和测试，避免未完成心跳确认时挂载主界面。
- 接口：严格对齐 `POST /api/client/activate`、`POST /api/client/heartbeat`、HTTP 恒 200 的 `{ code, data, msg }` 信封以及响应关联头；不改变服务端业务字段。
- 运维：后端仍以带下划线的请求头为权威契约；Nginx 必须配置 `underscores_in_headers on;`，或由后端显式兼容连字符别名。
- 测试：扩展 API 契约、错误矩阵、凭据迁移、生命周期和前端门禁测试，并增加日志泄密回归检查。
- 非目标：不实现生产信封加密、验证码处理、账号登录、服务端后台功能或任何直播平台访问控制绕过。
