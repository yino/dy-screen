## Context

AI 工作区目前有两个输入入口：“添加本地视频”通过系统文件选择器导入外部文件，“添加整场直播”通过 `recording_session` 选择历史录像。后端 `select_completed_session` 已经按会话展开登记视频，但界面语义和返回反馈不足以让用户确信这是整场操作，重复导入也不能稳定地完成其余分片。

录像会话与视频记录已经提供所需身份：`recording_sessions.id` 表示一场逻辑录制，`videos.session_id` 关联分片，`videos.started_at` 提供顺序。主播当前是否直播与历史会话是否结束是两个独立状态，不能用主播实时状态屏蔽历史数据。

## Goals / Non-Goals

**Goals:**

- 让用户以一场已结束直播为单位加入全部登记分片，不经过逐段文件选择。
- 主播当前直播时仍允许选择其历史已结束会话。
- 让整场导入可重试且对重复分片幂等，并提供新增、重复、不可用数量反馈。
- 继续使用统一输入列表完成逐段删除、排序和开始前检查。
- 保持后端对本地路径、会话完成状态和视频库身份的信任边界。

**Non-Goals:**

- 不导入当前仍在写入的直播会话或尚未封口的分片。
- 不把应用重启前后的多个 `recording_session` 自动合并为一场直播。
- 不在导入后自动运行 ASR，也不改变录制优先、ASR 单并发或取消策略。
- 不删除原始录像文件，不改变视频库和本地文件导入行为。

## Decisions

### 1. 以已结束 `recording_session` 作为整场导入边界

历史选择器继续查询 `ended_at IS NOT NULL` 的会话，并且不附加主播当前 `live_status` 条件。用户选择一个 `session_id` 后，后端重新读取会话并验证 `ended_at`，防止陈旧界面状态绕过检查。

选择该边界是因为它与现有录制生命周期、重试和视频归属一致。替代方案是按主播和时间间隔推断“同一场直播”，但应用重启、网络中断和跨日直播会让推断不可验证，第一版不采用。

### 2. 后端决定整场成员和稳定顺序

前端只提交受信的 `project_id` 与 `session_id`，不得提交任意分片路径或自选视频 ID。后端一次取得该会话全部登记视频，并按 `started_at ASC, id ASC` 排序后生成输入；不可用视频也保留对应视频库 ID 和顺序。

这避免前端列表过期、漏段或伪造本地路径。替代方案是在前端获取分片列表后逐项调用本地导入接口，但会扩大授权面并产生部分选择语义，因此不采用。

### 3. 整场导入采用逐项幂等结果

command 返回结构化导入结果，至少包含更新后的项目详情以及 `added_count`、`duplicate_count`、`unavailable_count`。已经存在于项目中的同一视频库分片或相同源指纹记为重复并跳过，不中止其他分片；缺失、损坏、未完成或无音轨分片加入列表并标记不可用。

媒体探测需要异步执行，不在长 SQLite transaction 中持有锁。若发生不可恢复的 repository 错误，调用返回错误；此前已加入的项目输入保持有效，用户重试时由幂等规则跳过。相比全有或全无事务，这更适合长直播和文件系统状态变化，也避免长时间阻塞录制数据库写入。

### 4. UI 保持两个明确入口

“添加本地视频”继续打开系统多选文件选择器。“添加整场直播”展示会话级选项，选项包含主播、起止时间、分片数、总时长和不可用数量；点击添加后直接导入整场，不打开分片选择器。导入完成后，统一输入列表展示每个分片，用户可删除或调整顺序。

主播当前直播时，历史已结束会话仍在选择器中；当前活动会话不作为可选项。反馈文案明确显示新增、重复和不可用数量，避免“只加入了一段”的误解。

### 5. 导入与执行状态继续解耦

整理历史回放只读取视频库元数据并探测已结束文件，不受当前录制门控影响。只有用户点击“开始分析”后才创建 ASR 队列任务；如果仍有任何直播录制，任务继续按现有策略显示等待录制结束。

## Risks / Trade-offs

- [长直播包含大量分片，逐项 FFprobe 可能让导入耗时明显] → 保持操作可取消、显示 busy 状态，并在完成后给出数量汇总；实现和测试避免阻塞 UI 线程。
- [文件在列出会话后被移动或删除] → 后端导入时重新检查，并把对应输入标记为不可用，不静默跳过。
- [部分导入后发生数据库错误] → 已加入输入保留，重试依靠视频 ID/源指纹幂等跳过，避免重复。
- [“整场”不跨应用重启合并多个会话] → 在选择器中展示明确起止时间和会话身份；跨会话组合继续由用户向同一项目添加多场完成。
- [主播当前直播时用户误以为历史 ASR 会立即运行] → 历史选择和输入管理保持可用，但开始分析后的状态继续明确显示录制优先排队原因。

## Migration Plan

不需要数据库 migration。先扩展 service/command 返回结构和测试，再更新前端适配与交互测试。旧项目及已有输入保持可读；若需要回滚，可恢复旧 command 返回和前端调用，录像会话与项目数据无需转换。

## Open Questions

无。跨会话自动归并和活动会话增量导入留待后续独立变更。
