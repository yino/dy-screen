## ADDED Requirements

### Requirement: 按持久化优先级分配录制名额
系统 SHALL 为所有未归档主播维护稳定且可由用户调整的录制优先级，并 SHALL 只从已开启监听且当前确认为直播中的主播中，按优先级和稳定次序选取不超过当前服务端额度的录制目标；未入选主播 MUST 继续状态监听，不得因没有录制名额而被暂停。

#### Scenario: 多个直播主播超过录制额度
- **WHEN** `a`、`b`、`c`、`d`、`e`、`f` 均在直播，当前额度为 4，优先级顺序为 `a,b,c,d,e,f`
- **THEN** 系统录制 `a,b,c,d`，并让 `e,f` 保持“直播中、等待录制资源”且继续检查直播状态

#### Scenario: 用户调整直播主播优先级
- **WHEN** 当前录制集合为 `a,b,c,d`，用户把 `e` 调整到 `d` 之前
- **THEN** 系统将目标集合立即重算为 `a,b,c,e`，优雅停止 `d`、保留其已完成分片并记录用户优先级切换原因，待其许可释放后重新解析 `e` 的最新地址并开始新会话

#### Scenario: 高优先级主播下播
- **WHEN** 当前录制目标中的主播下播，且仍有较低优先级主播在线等待
- **THEN** 系统关闭下播主播会话、释放名额，并自动为下一位仍在线主播重新解析地址后开始录制

#### Scenario: 高优先级主播未开播
- **WHEN** 高优先级主播当前离线，而较低优先级主播在线
- **THEN** 离线主播不占用录制名额，系统按在线候选的优先级继续补足额度

#### Scenario: 重启后恢复优先级
- **WHEN** 用户调整优先级后重启应用或主播进入下一次直播场次
- **THEN** 系统恢复同一优先级顺序，并根据最新在线状态和服务端额度重新计算录制目标

#### Scenario: 迁移现有主播
- **WHEN** 旧数据库尚无录制优先级字段
- **THEN** migration 保留全部主播、监听开关、会话和视频，按主播 ID 升序生成确定性优先级，并把之后新增的主播追加到末尾

#### Scenario: 优先级保存失败
- **WHEN** SQLite 无法原子保存用户提交的优先级变更
- **THEN** 系统保留原优先级和当前录制集合，向界面返回可重试的脱敏错误，不执行部分抢占

### Requirement: 在所有调用上下文安全启动监听任务
系统 SHALL 通过应用拥有的异步运行时调度器启动监听 worker，MUST NOT 假设调用线程已经进入 Tokio reactor；立即检查、恢复监听、访问恢复、系统唤醒、主播合并和启动恢复 SHALL 复用同一幂等启动入口。

#### Scenario: 系统唤醒回调缺少当前 Tokio reactor
- **WHEN** Tauri `RunEvent::Resumed` 在主线程触发全部立即检查，且某个已启用主播尚无 worker
- **THEN** 系统通过应用运行时成功创建该主播的唯一 worker，不发生 `there is no reactor running` panic 或进程退出

#### Scenario: 同步 command 缺少当前 Tokio reactor
- **WHEN** 用户从同步 Tauri command 触发单个主播立即检查
- **THEN** 系统安全唤醒既有 worker 或通过应用运行时创建新 worker，并向 command 返回结构化结果

#### Scenario: worker 创建失败
- **WHEN** 应用运行时已经关闭或调度器拒绝新任务
- **THEN** 启动入口返回脱敏错误，不在 worker 表中留下虚假任务，不污染监听开关且不触发进程级 panic

#### Scenario: 并发启动同一主播
- **WHEN** 多个入口近同时请求启动同一个主播
- **THEN** 系统只保留一个当前 generation 的 worker，其余请求仅唤醒该 worker

## MODIFIED Requirements

### Requirement: 限制全局并发录制
系统 SHALL 使用服务端下发的运行时全局额度限制并发录制数量，尚未从 AppStart 或心跳取得合法 `max_screen_limit` 时默认最多同时录制 4 个直播间；本地设置、旧数据库值和前端请求 MUST NOT 提高或降低该额度。

#### Scenario: 并发额度已满
- **WHEN** 新主播开播但当前服务端额度已由更高优先级录制占用
- **THEN** 系统显示“等待录制资源”，继续确认其直播状态，并仅在进入目标集合且获得许可后重新解析地址再开始录制

#### Scenario: 服务端提高运行时额度
- **WHEN** AppStart 或心跳把额度从 4 更新为 6，且至少有 2 个仍在线主播正在等待
- **THEN** 新额度立即生效，系统按优先级为下一批候选重新解析地址并补足名额，无需重启应用

#### Scenario: 服务端降低运行时额度
- **WHEN** AppStart 或心跳把额度从 4 更新为 3，且当前有 4 路活动录制
- **THEN** 系统优雅停止最低优先级的超额录制、保留完成分片，并在其释放许可前不启动替代录制，使活动录制数最终不超过 3

#### Scenario: 本地旧设置与服务端额度冲突
- **WHEN** 旧数据库或前端设置载荷包含不同的 `max_concurrent_recordings`
- **THEN** Supervisor 忽略本地值并只使用当前服务端额度或默认值 4
