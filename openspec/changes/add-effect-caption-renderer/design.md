## Context

见 `proposal.md` 的 Why。与设计相关的现状约束：

- 现有字幕渲染是 Rust 侧 `fontdue` 光栅化到 RGBA PNG 序列，再经 `ffconcat` 清单交给 FFmpeg `overlay`（`src-tauri/src/ai/clip_subtitle.rs`、`src-tauri/src/ai/clip_export.rs`）。字形来自平台系统字体候选列表，因此“字体锁定”目前并不成立。
- `ai-clip-subtitles` 已提交“固定样式”与“预览与导出使用相同计划”两条要求，本 change 需要在不放弃它们的前提下容纳特效字幕路径。
- 本 change 依赖 `add-model-gateway-and-harness-sidecar` 提供的 sidecar 与统一模型调用点（客户端持 `ai/llm-ak` 短期 token 直连百炼），**不依赖任何服务端网关令牌**。
- 该 change 同时推翻了归档变更中“不引入 Node.js 或 Node sidecar”的决策；推翻理由已记录在该 change 的 `design.md`，本 change 承接其代价（新增运行时组件）。**改用本 change 选定的渲染后端不改变该推翻结论**——渲染后端仍需要进程外运行时与浏览器。
- 渲染后端 HyperFrames 会向被渲染页面注入自带的、钉版本的引擎脚本。这是本 change 信任边界表述的事实基础，不能用“生成物不可执行”掩盖。

## Goals / Non-Goals

**Goals:**

- 让特效字幕在用户设备上可执行、可复现、可取消、可缓存，并把**模型侧产出**限制为不可执行的声明式内容，使静态校验的失败模式可穷举。
- 如实描述并约束信任边界：页面中的可执行内容仅来自随包渲染器的钉版本引擎脚本，且该运行时必须通过完整性校验。
- 在不放弃基础字幕既有语义的前提下，让两类字幕共用同一套透明层合成与固定 FFmpeg 模板。

**Non-Goals:**

- 不让模型决定渲染参数、滤镜、目录布局或依赖。
- 不让模型提供、替换或参数化任何脚本。
- 不以平台系统字体渲染特效字幕。
- 不为特效字幕引入远程字体、远程媒体或在线依赖安装。
- 不实现生成式动画分支。
- 不引入服务端网关令牌。

## Decisions

### 决策一：生成物为受限 HTML/CSS，渲染后端为 HyperFrames，并把随包引擎脚本计入信任边界

**选择**：模型生成纯声明式的受限 HTML/CSS 组合（模型 MUST NOT 生成脚本），由 HyperFrames（Apache-2.0）在 headless Chrome 中逐帧渲染，以 `png-sequence` 格式直接输出 RGBA 帧序列。**被渲染页面中存在 HyperFrames 自带的、随包钉版本的引擎脚本**——这是已知事实，必须在信任边界中显式承认。

**这是对本次 change 前一版决策的修正。** 前一版选择“生成受限 Remotion TSX + AST 校验”。修正理由按分量排序：

1. **许可。** Remotion 是源码可见的商业许可并按公司规模设门槛，对一个包月/包年的商业产品构成实质风险；HyperFrames 是 Apache-2.0，该风险消失。
2. **模型侧风险降级。** TSX 是任意 JavaScript，前一版因此不得不承认“必须在用户设备上执行模型生成的代码”。改为纯声明式 HTML/CSS 且由白名单校验显式拒绝脚本后，**模型无法把可执行内容写进组合**：校验从“给任意 JS 做静态分析”变成“标签、属性、CSS 属性与取值的枚举校验”，失败模式可知可穷举。这是风险性质的降级，不是程度的改善。
3. **透明中间产物原生可用。** 渲染后端直接提供 RGBA PNG 帧序列输出，且把页面背景强制为透明，正好是本 change 已固定的中间格式，无需另行配置或后期抠色。
4. **无构建步骤。** 组合文件在浏览器中直接播放，生成物到渲染之间不存在打包器、依赖解析或安装步骤。

**关于“不可执行”的更正。** 前一版把结论写成“HTML/CSS 组合在禁止脚本后是不可执行的”，并据此把进程隔离列为“仍然必需”。这句话只对**模型生成物**成立，对**被渲染的页面**不成立：渲染器会注入自己的引擎脚本。因此：

- 准确表述是：“模型不得产出任何可执行内容；页面中可执行的内容仅限渲染器自带的、钉版本的引擎脚本，且该运行时必须通过完整性校验。”
- 本 change MUST NOT 使用“生成物完全不可执行”来论证页面安全。

**决策成立的四条约束**（由三条扩为四条，任何一条被削弱都应重新评估）：

1. 静态校验与进程隔离同时存在；
2. 组合只能引用随包资源、不得引入任何外部引用；
3. 分辨率、字体与浏览器版本锁定并由缓存键约束；
4. **渲染器运行时完整性校验**：渲染前按随包清单校验渲染器二进制、渲染浏览器与引擎脚本的哈希与版本，任一不符即拒绝渲染；**引擎脚本版本进入渲染缓存键**。

**已考虑的替代方案**：

1. **受限 Remotion TSX**（前一版的选择）。技术上可行且生态成熟，但需先确认商业许可是否适用，且可执行面来自模型生成的任意 JS。
2. **Rust 声明式模板**（扩展现有 `fontdue` → RGBA PNG → `ffconcat` → `overlay` 链路）。优势明确：模型侧零执行风险、逐帧一致、不需要额外运行时、不推翻任何已归档决策。仍未采纳的原因与前一版相同——目标视觉质量依赖自由编排的时序与合成，声明式模板在表现力上存在上限，而特效字幕是主要产品卖点之一。

**未经验证的假设**：本决策基于文档而非实测。渲染后端的实际表现（纯 CSS 能达到的表现力、渲染耗时、帧序列体积）由迁移计划第 2 步先验证；若验证不通过，第 2 条替代方案就是退路。

### 决策二：可执行内容的来源钉死为随包渲染器，模型侧一律禁止脚本

**选择**：模型生成的组合 MUST NOT 包含脚本、事件处理器属性、脚本引用或构建配置。允许执行的内容只有一种：随包、钉版本、经完整性校验的渲染器引擎脚本。

**理由**：前一版把“钉版本的本地动画库”写成表现力不足时可放宽的例外；在承认渲染页面存在引擎脚本之后，正确的做法不是“预设禁止一切脚本”，而是**把可执行内容的来源钉死为渲染器自身**。这样既保留渲染后端的能力，又不给模型任何进入可执行面的入口。

**若表现力仍不足**：只能在渲染器自身已提供的能力范围内放宽（例如启用其已有的、钉版本的高阶 API），MUST NOT 允许模型提供、替换或参数化脚本；任何放宽都需要独立评审并重新做越界样本验收。

**约束**：引擎脚本不得由模型写入、替换或通过组合参数影响；渲染器版本或引擎脚本版本变化必须使发布校验与渲染缓存同时失效。

### 决策三：白名单校验替代 AST 校验

**选择**：校验标签、属性、CSS 属性与取值、元素数量与嵌套深度、动画时长与帧数上限、文本引用，并显式拒绝脚本、事件处理器属性、脚本引用与任何指向随包资源之外的外部引用。

**理由**：可执行内容不在模型产出里，所以校验不需要理解控制流或作用域，只需枚举允许的构造。这比给任意 JS 做静态分析更可靠，也更容易验证（拒绝路径可以按构造逐类穷举）。**但校验只覆盖模型侧**；页面中引擎脚本的可信性由决策一的第 4 条约束（运行时完整性校验）保证。

### 决策四：一致性按“同一计划、不同分辨率”定义

**选择**：预览与导出使用相同的组合版本、文本、字体、时间计划与相对布局，只允许渲染分辨率不同。

**理由**：原要求“相同计划”的本意是防止预览与成片出现内容或布局差异，而不是禁止分辨率差异。按此定义，要求可被满足且仍然有约束力。

**约束**：组合版本、文本或字体在预览后发生变化时，导出必须重新渲染并更新记录，不得复用与当前版本不符的帧。

### 决策五：透明中间产物使用渲染器原生 RGBA 帧序列，不使用色键

**选择**：直接采用渲染后端输出的 RGBA PNG 帧序列，完全依赖其真实 Alpha 通道；最终编码阶段才转为 `yuv420p`。

**理由**：色键抠图会在半透明边缘、抗锯齿文字和阴影处产生明显瑕疵，而特效字幕恰恰大量使用这些效果。真实 Alpha 是这条链路的质量底线。

**附带约束**：组合不得为根元素绘制不透明全屏背景，否则透明中间产物不可用。

## 适用性验证结论（第二步实测，2026-09-30）

完整证据见 [`sandbox-feasibility.md`](sandbox-feasibility.md)（第一轮 + 第 11 节复测）。**进入条件裁决：通过**，但成立条件比原设想更窄，必须按下列约束实施。

**A 表现力：通过。** 纯 CSS 组合的 motion energy 为固定样式基线的 1.6–4.5 倍，色相跨度 0 → 73–113，包围盒高极差比 1.09 → 1.27–32.88。决策二的表现力放宽评审**不触发**。

**B 耗时：通过，但只在一种捕获形态下成立。**

| 捕获形态 | 15s | 30s | 结论 |
| --- | --- | --- | --- |
| 渲染器原生 `png-sequence`（全画布） | 4.810 | 3.138 | ❌ 慢 3–5 倍 |
| `page.screenshot({clip})` 带裁剪（视口仍全屏） | 1.070 | 1.024 | ❌ 仍慢于实时 |
| **视口高度 = 带高的小 surface + ffmpeg overlay 合成** | **0.867** | **0.847** | ✅ **选定路径** |

根因：每帧成本由**固定开销**主导，全画布捕获面积降到 1/4.8 只省 12–33%。渲染器原生路径在 CDP 层强制 `captureBeyondViewport: true` 与 `optimizeForSpeed: false`，且其快速捕获模式在本机未生效。

**C 体积：可接受。** 带路径输出 135–138 KB/帧（≈4.1 MB/s），90 秒约 370 MB；比全画布直捕的 2.5 MB/s 大 60%，仍在 8 GB 设备可承受范围（按高光分段渲染与即时清理）。

**必须记录的约束：**

1. **捕获形态固定为"视口高度 = 字幕带高度"的小 surface + 外部 ffmpeg overlay 合成**；MUST NOT 使用全画布捕获，也 MUST NOT 使用 `clip` 裁剪。
2. 带区域按 1080×400（全画布 20.8%）设计，**MUST 保证字幕不越出该带**；越出即被裁切。
3. 30 fps 为上限；60 fps 外推比值 ≥1.7，MUST NOT 支持。
4. 合成 MUST 使用 `-start_number 0`，否则整条序列错一帧。
5. **确定性的口径是逻辑确定性，不是位精确。** 规格要求"固定动画随机源，使同一输入能够重现相同的画面结果"，被拒绝的是依赖真实时钟、未固定随机源与非确定性布局测量；而决策四已确定"预览与导出仅分辨率不同"，跨分辨率位精确在结构上不可能。因此：同一输入下**动画状态与布局必须唯一确定**，允许约 0.4–0.9% 的帧存在合成器光栅差异。**位精确并非本 change 的要求**；若未来需要位精确，需每帧增加一帧 rAF 同步，代价是比值升到 1.049 而不再满足 B。
6. 该路径需要扩展渲染器集成面：现有 alpha 捕获把 clip 硬编码为全画布并启用 `captureBeyondViewport`，须改为"带捕获 + 外部合成"。

**未验证项**：8 GB 目标设备未实测（本机 M3 Pro/36GB），带路径在弱机上是否仍 <1.0 不可外推，必须在目标机型复测。

### 决策六：渲染器运行时完整性校验与版本四重锁定

**选择**：渲染前按随包清单校验渲染器二进制、渲染浏览器与引擎脚本的哈希与版本；特效字幕使用随包锁定字体，动画随机源固定；**字体、浏览器版本、渲染器版本与引擎脚本版本共同进入缓存键**。

**理由**：现有基础字幕依赖平台系统字体，不同设备会产生不同字形与换行；浏览器与渲染器版本同样影响栅格化与抗锯齿结果。更重要的是，在页面存在引擎脚本的前提下，**不校验运行时就无法断言执行的是随包可信代码**——校验失败必须导致明确失败，而不是静默降级到未校验的运行时。

**范围**：本决策先覆盖特效字幕路径；基础字幕是否一并切换到锁定字体由后续评估决定。

### 决策七：抑制区间由工程句段决定

**选择**：特效字幕只声明覆盖哪些句段，实际抑制区间由工程已发布句段的真实时间范围计算。

**理由**：模型给出的时间戳不可定位、不可校验；以句段为单位则天然与人工编辑保持一致——用户新增或修改字幕会导致抑制区间重新计算。

### 决策八：降级保留单一最终增强方式

**选择**：校验、渲染或合成失败时，该高光降级为普通原视频与基础字幕，并记录最终唯一的增强方式与原因。

**理由**：两条分支同时进入导出会造成两层文字；必须有一个明确且唯一的终态。

## Risks / Trade-offs

- [新增信任边界（最高优先级）] 被渲染页面中存在渲染器自带的引擎脚本，渲染器与浏览器是真实执行的组件 → 决策一的四条约束、决策三的可穷举拒绝路径、决策六的运行时完整性校验，以及任务中“越界组合被拒绝 + 引擎脚本被篡改时拒绝渲染”的可复核证据。
- [依赖成熟度] 渲染后端为较新项目且自述快速演进 → 钉死版本、把集成面限制在“组合输入 + RGBA 帧序列输出 + 退出码”窄面、不深度集成其高级能力；引擎脚本清单与版本随包固定；迁移计划第 2 步先做适用性验证。
- [禁脚本的表现力上限] 纯 CSS 可能不足以表达目标效果 → 决策二给出“只允许渲染器已有能力”的放宽路径，且要求独立评审；探针先测出纯 CSS 的上限。
- [浏览器打包成本] 渲染后端需要捆绑固定版本浏览器，安装包体积与 8 GB 设备峰值内存的代价**与是否选用本方案无关**，它来自“用浏览器渲染 DOM”这一路线本身 → 纳入资源清单与实测；这一代价在决策一的替代方案 2（Rust 声明式模板）下不存在，因此保留为重新评估本决策的触发条件之一。
- [完整性校验的失败模式] 校验失败会导致增强能力不可用 → 明确失败并给出可区分诊断，不静默降级到未校验运行时；录制、浏览、预览与本地 ASR 不受影响。
- [磁盘与 IO 峰值] 全分辨率 RGBA 帧序列体积大 → 按高光范围分段渲染、成功后立即清理、并发受限；任务中要求在 8 GB 目标设备上测量峰值磁盘占用。
- [预览与导出的视觉差异] 低规格预览可能掩盖高规格下的排版问题 → 缓存键包含分辨率、帧率、浏览器版本、渲染器版本与引擎脚本版本，且任务中要求对同一高光分别以预览与导出规格渲染并核对相对布局。
- [与既有字幕语义的冲突] “固定样式”要求只应约束基础字幕 → 规格中以能力边界明确区分两类字幕，避免被理解为放开基础字幕的样式约束。
- [周期与依赖] 本 change 依赖 sidecar 先行交付 → 任务按“校验 → 渲染 → 合成 → 发布校验”分层，使校验与渲染可在 sidecar 就绪前用固定样本推进。

## Migration Plan

1. **前置**：`add-model-gateway-and-harness-sidecar` 的 sidecar 与统一调用点可用（模型调用为客户端直连百炼）。
2. **适用性验证（沙盒，可与前置并行）**：在仓库之外的临时工程中验证三件事——纯 CSS 组合能达到的表现力上限、单条高光的渲染耗时与高光时长的比值、全分辨率 RGBA 帧序列的体积。**这一步是本 change 的进入条件**：若表现力不足以明显优于现有逐字字幕，或渲染慢于实时，或帧序列体积不可接受，则回到决策一的替代方案 2，而不是继续本 change。
3. **引入校验与渲染**：以固定样本组合打通白名单校验、运行时完整性校验与受限渲染，验证拒绝路径与资源限制，不接入真实生成。
4. **接入生成**：接入字幕组合 Skill 与增强方式选择，先在单条高光上端到端验证。
5. **合成与抑制**：扩展导出链路支持 RGBA 帧序列与基础字幕抑制，验证两类字幕不叠加。
6. **发布校验**：把 RGBA/alpha PNG 解码能力加入 FFmpeg 能力审计，把渲染运行时、固定版本浏览器与锁定字体加入随包必需组件，并把渲染器运行时完整性校验纳入发布校验与 macOS arm64、macOS Intel x86_64、Windows x64 的离线启动验收。
7. **回滚**：特效字幕为可选增强，关闭后该高光退化为普通原视频与基础字幕；基础字幕链路与本 change 前完全一致，因此回滚不丢失任何既有能力。

## Open Questions

- 纯 CSS 的表现力是否足够（决策二的放宽是否会被触发）。这由迁移计划第 2 步给出证据，不改变本 change 已固定的契约。
- 渲染器运行时完整性校验的具体形式（清单哈希、签名校验或两者并用），以及引擎脚本清单的粒度（单文件还是按包）。契约已要求“任一不符即拒绝渲染且版本进缓存键”，形式可在实现时确定。
