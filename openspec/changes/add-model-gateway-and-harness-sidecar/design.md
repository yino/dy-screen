## Context

见 `proposal.md` 的 Why。与设计相关的现状约束：

- 现有 LLM 调用是单次结构化输出，没有工具循环：`src-tauri/src/ai/llm.rs` 使用 `rig-core` 的 extractor 构造一次性请求；`MAX_AGENT_TURNS` 是未被使用的常量。“Agent”与“Skill”目前是提示词组织方式，不是可执行单元。
- `DEEPSEEK_BASE_URL` 是硬编码常量，`LlmProviderSettings::validate()` 拒绝非 `deepseek` 的 provider；用户的上游 Key 保存在操作系统凭据库中，被精彩分析、转场匹配与文本纠错三条链路直接使用。
- 客户端已有 `GET /api/client/ai/llm-ak`，返回 `{ak, expireAt, provider}`，`provider=ALI`，`ak` 形如 `st-lt-v1.xxx` 的短期 token。该 token 的设计用途就是客户端直连上游，本次直接复用它，不再要求用户自备 Key。
- 客户端不存在任何 sidecar 之外的进程外 Agent 运行时，`src-tauri/tauri.conf.json` 没有声明 `externalBin` 或 `resources`；运行资源由签名清单驱动的独立资源包提供，组件集是闭合枚举。
- `src-tauri/src/ai/domain.rs` 的阶段枚举为输入预检、本地 ASR、精彩发现与评分、草稿、纠错、转场、审阅七个阶段。
- v2 口径已定案：admin-service 本轮不新增任何接口，也不做服务端分项账本；因此本 change 不引入服务端模型网关。

## Goals / Non-Goals

**Goals:**

- 建立一个受控、版本固定、可取消、可回收的进程外 Harness 运行时，能按职责组织 Skill 并被授予受限业务工具。
- 让全部模型调用统一走“客户端持短期 token 直连百炼”的单一形态：凭据不进入 WebView，客户端不再要求用户自备 Key。
- 让配置切换可预期（最长一个心跳周期生效）、运行内冻结、历史结果按运行指纹匹配，并在保证三条既有链路行为不回退的前提下完成模型来源迁移。
- 在 macOS arm64、macOS Intel x86_64 与 Windows x64 三个架构上完成协议与恢复验收。

**Non-Goals:**

- 不引入服务端模型网关、网关短期令牌或“本机直连 / 经网关”两条路径的解析。
- 不新增服务端接口，不做服务端 token 用量记账（`add-cloud-ai-job-backend` 已搁置）。
- 不实现两条增强分支本身（特效字幕与生成式动画），只提供它们所需的 Skill 承载与媒体生成工具契约。
- 不改变精彩分析、转场匹配与文本纠错的校验规则、阈值语义、结果结构或冻结代次机制。
- 不把本地 ASR 的云端路径并入本 change（已由 `wire-cloud-asr-upload-and-jobs` 交付）。
- 不在客户端实现特效字幕的组合渲染。

## Decisions

### 决策零：正式推翻两条已归档决策

本 change 依赖两项能力，而这两项能力在已归档变更中被明确列为非目标，因此在此记录推翻理由、替代方案与代价。

**被推翻的决策一**：`2026-07-26-improve-ai-clipping-agent-workflow` 的 proposal 与 design 记录“不引入 Node.js、浏览器端密钥或 Node sidecar”“不打包 Node.js、不使用 `vercel/ai`、不在 WebView 中调用 DeepSeek”。

**被推翻的决策二**：`2026-08-09-implement-clip-agent-and-text-correction` 的非目标记录“不让 Agent 生成素材或任意渲染参数”。

**推翻理由**：

1. 原决策一的合理内核是“不在 WebView 中调用模型、不让浏览器持有密钥”，这一点在本 change 中被完整保留甚至加强：模型调用只发生在 Rust 侧，短期 token 只在 Rust 内存中持有，WebView 不接触任何凭据。
2. 原决策一的另一部分是“不打包 Node sidecar”，其代价模型是“少一个运行时即少一份体积与供应链面”。但 v2 的特效字幕与生成式动画要求按职责组织 Skill、需要工具循环与流式增量；这些能力在现有单次结构化输出结构上无法承载。引入进程外运行时因此成为承载新能力的最低成本路径。
3. 原决策二的合理内核是“不让模型自由决定渲染参数与素材”。本 change 保留该内核：Agent 只能提交结构化请求，Rust 侧校验时间、互斥类型、调用次数与额度上限，Agent 不持有凭据也不持有任意下载地址。

**已考虑的替代方案**：

1. **在 Rust 内实现受限 Agent 循环**（不引入进程外运行时）。这保留原决策，但需要自行实现工具循环、流式增量与 Skill 组织，且要求所有 Skill 逻辑用 Rust 表达；对以受限组合为产物的特效字幕分支不成立。
2. **只做服务端 runner**。被否决：与“客户端 Harness 只服务所在设备”“不为桌面任务常驻服务端 Agent”冲突，并把用户媒体处理搬到服务端，扩大隐私面。

**代价**：增加一个随包运行时组件（体积、供应链面、三个架构的协议与恢复测试），并需要把该组件纳入运行资源清单与发布校验。这些代价由 `add-effect-caption-renderer` 与 `add-generative-video-animation` 共同承担。

### 决策一：Harness 以进程外子进程承载，Rust 为状态权威

**选择**：Rust 启动并监管独立子进程中的 Harness，经进程外 JSON-RPC 通信。

**理由**：进程外才能分别限制资源、独立取消与回收，也才能让“sidecar 崩溃不等于任务状态损坏”成立。把状态权威留在 Rust 意味着 sidecar 的运行记录只用于诊断。

**已考虑的替代方案**：进程内嵌入。被否决：无法在资源超限时安全终止，且崩溃会带走任务状态。

### 决策二：传输使用 stdio 上的 JSON-RPC，而非本地 HTTP

**选择**：通过被监管子进程的标准输入输出交换 JSON-RPC 消息。

**理由**：不需要监听端口，因而不存在本机其他进程可访问的接口；进程生命周期与连接生命周期天然绑定；“仅服务所在设备”的边界自动成立。

**已考虑的替代方案**：本地回环 HTTP。被否决：需要额外鉴权来防止本机其他进程调用，且端口冲突与残留监听是常见故障。

### 决策三：应用专用 Profile，不使用用户全局配置

**选择**：只使用随应用打包的 Profile 与 Skill，忽略用户目录下的同名配置。

**理由**：用户全局配置不可控且不可复现；生产 Profile 必须能声明“只有这些工具”。

### 决策四：模型调用是单一形态——客户端持短期 token 直连百炼，配置在心跳周期边界解析并在运行前冻结

**选择**：模型调用只有一条路径：客户端 Rust 侧从 `GET /api/client/ai/llm-ak` 取得短期 token，直连百炼的兼容端点与原生端点。一个统一的**调用点**把「Base URL、模型标识、受控请求参数」解析为一个**不可变快照**；解析在每个心跳周期边界进行，**配置切换接受最长一个心跳周期（90 秒）生效**，快照在运行开始前冻结，**进行中的运行不受配置切换影响**。

**本决策修正本 change 前一版**：前一版把“本机直连上游”与“经服务端网关”定义为两条一等公民路径，并按四层来源解析。该形态需要服务端提供 `runs` 与模型网关接口以及服务端 token 记账，与“admin-service 本轮不新增任何接口”的口径直接冲突；对应实现整体保留在已搁置的 `add-cloud-ai-job-backend` 中。

**理由（按分量）**：

1. **口径已经定案，单一形态是唯一可验收的形态。** 服务端不再提供网关与记账权威，保留“两条路径”只会形成无法交付的空契约。
2. **冻结是必需的，不是优化。** 已提交的 `ai-highlight-agent-workflow` 要求候选发现与全局评分使用**同一个模型**。如果模型是运行期可变的，一次运行的两个阶段可能取到不同值，该要求立即失效。同时，不冻结就无法给缓存键与运行指纹一个稳定值，切换后会拿旧模型的结果冒充新模型的结果。
3. **短期 token 复用既有语义。** `ai/llm-ak` 的设计用途就是客户端直连上游；沿用它可以不新增接口、不改动激活与心跳契约。
4. **90 秒是有意的取舍。** 按心跳周期解析让配置切换不需要发版，同时把“配置切换多久生效”变成一个明确、可测的承诺；进行中的运行按冻结快照执行，避免中途换模型。

**关于“写成全局变量”**：可变全局是实现“改一处即生效”最直觉的形态，但它有两个具体问题——并发运行会互相污染配置；测试无法为单个用例指定模型。更关键的是它直接破坏上面第 2 点的“同一模型”要求。用户真正想要的效果（改一处即生效、一处可查）由「一个调用点 + 一处配置入口 + 来源记录」满足，不需要可变全局。全局只保留为**不可变的兜底默认值**。

**已考虑的替代方案**：

1. **服务端模型网关 + 服务端记账**（本 change 前一版的选择，对应已搁置的 `add-cloud-ai-job-backend`）。被否决：需要新增服务端接口与分项账本，与 v2 口径冲突；服务端不可用时整条链路不可用。
2. **保留“本机直连 / 经网关”双路径与四层解析**。被否决：口径已取消网关，保留解析层级只会带来误配风险，且没有可验收的服务端实现。
3. **每次调用现读设置**。被否决：一次运行内会出现模型漂移，缓存与指纹失去意义。

**关于安全边界的处理**：主规格 `llm-provider-configuration` 已提交“MUST NOT 接受任意 Base URL、代理地址”。这条**保留在生产构建**，否则等于把客户端交给任意重定向目标。短期 token 只取自 `ai/llm-ak`，生产构建不接受手输凭据或手输 Base URL；开发与验证构建可通过本地配置文件或环境变量覆盖，且非生产配置必须在界面与诊断中显著标记。

**该分级必须是编译期判定的**，不能是运行时可翻转的标志位或配置项——否则它就不是边界，只是一个默认值。生产构建里自由输入的代码路径应当直接不存在，而不是被一个条件挡住。

**重启与历史资产**：重启后重新解析模型配置；已发布结果按产出它的运行指纹匹配，**指纹不一致时保留为历史建议、不自动应用**，避免丢弃已付费资产。

**接受的代价**：客户端承担直连的可用性与重试责任；配置面仍然存在（构建期默认、本机覆盖、心跳周期解析），需要“非生产配置显著标记”来防止误配跟着正式包发出去；解析来源必须可观测，否则排查“为什么这次用了另一个模型”会变成猜谜。

**已实测确认的凭据复用与端点（`validate-dashscope-direct-capabilities`）**：同一个 `ai/llm-ak` 短期 token（`provider=ALI`）实测可用于四类调用——通义兼容模式对话、万相文生图、万相图生视频与百炼文件转写。LLM 调用实测走 `POST /compatible-mode/v1/chat/completions`（模型 `qwen-plus`），返回 `http=200` 与正常回复，`usage` 含 `prompt_tokens`/`completion_tokens`/`total_tokens`。因此三条既有链路（精彩分析、转场匹配、文本纠错）改用统一调用点取短期 token 后，**不需要任何新增服务端接口**，也不需要单独的网关令牌。记账依据只取上游响应 `usage` 中的 token 字段；上游不具备调用方幂等能力（实测同参数两次提交得到两个不同 `task_id`），重复提交的去重责任在客户端本地。

### 决策五：三条旧链路改为经统一调用点调用，而不是各自维护地址与模型

**选择**：精彩分析、转场匹配、文本纠错不再各自决定 Base URL 与模型，全部改为向统一调用点取“短期 token + 冻结模型快照”；三条链路的行为、校验规则、阈值语义与冻结代次机制保持不变。

**理由**：这三条链路今天各自读取设置、各自持有上游地址（`DEEPSEEK_BASE_URL` 是硬编码常量，且 Provider 校验只接受单一取值）。只要有一个模块绕过调用点，“切换模型只改一处”就会退化成“改多处”，而且三条链路的凭据与错误口径会分叉。

**转换顺序**：按风险从低到高——文本纠错（输入文本有界、失败无副作用）→ 转场匹配（结果可被人工覆盖）→ 精彩分析（链路最长、影响后续所有阶段）。每步以既有测试作为等价性断言。

**验证点**：转换完成后，切换模型只改一处配置；任何模块都不得直接读配置文件、环境变量或全局状态来决定模型；任何模块都不得自行获取短期 token。

### 决策六：媒体生成是受控业务工具，不是凭据

**选择**：Skill 只能提交结构化生成请求并取回业务任务 ID；短期 token、实际提交与下载地址都在 Rust 侧。

**理由**：把 token 暴露给模型可影响的一侧会同时破坏额度门禁与供应链边界。

### 决策七：数据边界从“全不上传”改为“两个显式例外”

**选择**：在 `desktop-client-shell` 的数据边界需求中明确两个且仅两个例外：经用户显式授权的临时音频直传百炼（云端转写用）与经用户显式授权的最小文本发往百炼（模型调用用）。

**理由**：原需求是无例外的 MUST NOT，而具体能力规格（`cloud-asr-provider`）已经隐含了音频例外。把例外收敛为两条并写在一个地方，比让每个能力各自开洞更容易审计。

**同时更新设置页语义**：设置页入口从“管理上游 API Key”改为“查看当前模型与可用性”，展示当前生效模型、解析来源、短期 token 状态与 heartbeat 判定的开通/额度状态；不再要求用户输入 Key。

## Risks / Trade-offs

- [直连可用性] AI 能力依赖百炼可达性与账号开通/额度状态 → 按 heartbeat 的额度与开通结论显示可用性；网络与额度错误使用可区分分类；本地 ASR 路径与录制、预览等基础能力不受影响。
- [既有凭据的处理] 升级后不再需要用户既有的上游 Key → 迁移只保留该凭据、不强制清除，避免破坏用户回退到旧版本；不得在日志或界面回显旧 Key。
- [配置面仍存在] 构建期默认、本机覆盖与心跳周期解析带来误配风险 → 解析来源必须可观测；非生产配置在界面与诊断中显著标记；生产构建拒绝手输地址与凭据。
- [90 秒生效窗口] 用户改配置后最长 90 秒才生效，可能被误认为“没生效” → 界面显示当前快照与下次解析时间；文档明确“进行中的运行不受影响”。
- [运行时协议处于开发者预览] 上游 Harness 协议可能变化 → 固定版本、把协议版本写入随包清单、要求三个架构分别通过协议与恢复测试后才允许升级。
- [运行资源清单的组件集是闭合枚举] 新增运行时组件会被发布校验拒绝 → 任务中明确要求扩展清单组件类型与校验，并同步更新发布校验的必需组件列表，覆盖 Intel x86_64。
- [三条链路迁移的回归面] 校验规则、冻结代次与结果结构必须保持不变 → 要求以既有测试作为迁移的等价性断言，并在任务中列出必须保持不变的断言项。
- [媒体生成工具的额度门禁] 门禁在客户端本地执行，缺少服务端拒绝 → 以 heartbeat 的额度/开通结论为上限，并在本地冻结配置中固定任务级上限；超限即不提交。
- [资源占用] 额外常驻运行时会影响 8 GB 目标设备 → 要求按需启动、空闲回收，并在任务中测量 Harness 与渲染进程的峰值内存与磁盘占用。

## Migration Plan

1. **前置**：`validate-dashscope-direct-capabilities` 的探针确认临时 token 可完成流式 LLM 调用；`wire-cloud-asr-upload-and-jobs` 已交付并能独立验收。
2. **引入运行时**：接入 sidecar、Profile 与 Skill 打包，先在诊断路径验证启动、JSON-RPC 往返与异常退出恢复，不改变任何业务链路。
3. **统一调用点**：实现短期 token 获取与内存持有、模型快照解析与冻结，把三条链路改为经调用点调用，保持当前生效配置不变，验证行为与切换前逐项等价。
4. **切换配置来源**：把模型与参数的来源切到“构建期默认 + 本机覆盖 + 心跳周期解析”，验证最长 90 秒生效、进行中的运行不受影响、指纹不一致时不复用旧结果。
5. **设置页与凭据**：把设置页入口改为“查看当前模型与可用性”；`llm_provider_settings` 新增模型来源与解析时间戳字段并保留阈值；既有上游凭据保留、不强制清除。
6. **回滚**：回滚只需把模型配置切回上一组取值，这是一次配置变更、不需要发版；本地识别路径与录制、预览等基础能力全程不受影响。
7. **发布校验**：把运行时组件加入随包清单与发布校验的必需组件，并在 macOS arm64、macOS Intel x86_64 与 Windows x64 上分别完成协议与恢复测试。

## Open Questions

- 生产构建的兜底默认模型取值，以及心跳周期内解析的具体触发时刻（心跳响应到达时还是周期计时器）。契约已固定“最长一个心跳周期生效、运行前冻结”，实现方式可在实现时确定。
- 短期 token 的提前刷新阈值（现有实现按剩余有效期不足 30 秒视为不可用）是否需要在三条链路统一。契约只要求“过期前刷新、不写入持久化存储”。
- 是否需要在界面暴露“立即重新解析”入口。契约允许它存在且不影响进行中的运行，是否开放给用户可在实现时决定。

- 进程外 Harness 运行时的具体技术形态与打包方式（随包运行时 vs 依赖系统已有运行时）。这不改变本 change 已固定的契约（进程外、stdio JSON-RPC、随包版本固定、忽略用户目录配置），可在实现前确定。
