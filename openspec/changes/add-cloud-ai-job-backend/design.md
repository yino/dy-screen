## Context

见 `proposal.md` 的 Why。与设计相关的现状约束：

- 服务端实现在独立仓库 `admin-service`（Next.js 14 App Router + Prisma + PostgreSQL + Redis），本仓库的 OpenSpec 只覆盖契约与客户端消费行为，不覆盖服务端代码。这是本次设计的最大约束：验收必须落在可观测的接口行为与账本数据上。
- 现有 AI 授权链路是"签发即脱手"：`GET /api/client/ai/llm-ak` 用服务端长期密钥签发短期令牌，客户端随后直连上游，服务端只按次数递增 `llm_used`，无法观测真实用量。
- 现有唯一幂等构造是 `llm_duration_usage_logs` 的 `(licenseId, usageId)` 唯一索引，覆盖单一资源，不足以支撑多类型付费任务。
- 现有对象存储实现只支持服务端上传，且使用 `public-read` 与永久公开地址，与临时音频的短期、受限要求相反。
- 客户端 `src-tauri/src/api.rs` 已提供单一 Rust API 客户端（`PlainJsonCodec` 明文 JSON），所有授权请求经它发出。

## Goals / Non-Goals

**Goals:**

- 让服务端成为四类付费调用（ASR、模型、图片、视频）的唯一付费入口与唯一记账权威。
- 在任何中断、崩溃、超时路径下都不产生重复付费：靠幂等键、待对账状态与按 `requestId` 找回共同保证。
- 让临时音频与生成资产的生命周期可查询、可清理、可重试，且不永久公开。
- 保持现有激活、心跳、录制与本地 ASR 行为不变，新增接口全部为增量。

**Non-Goals:**

- 不实现客户端侧的上传器、Harness sidecar、代码渲染与动画合成（分别在后续 change）。
- 不改变信封加密的进度：本期仍为明文 JSON，不实现 `encKey` 与请求签名。
- 不为桌面任务部署常驻服务端 Agent runner。
- 不实现管理后台的账本与预算展示界面。
- 不做上游图片与视频 Provider 的最终选型决策，只冻结调用契约与门禁语义。

## Decisions

### 决策一：服务端从"签发令牌"改为"代理并记账"

**选择**：模型调用经 `POST /api/client/ai/llm/v1/chat/completions` 由服务端代理，服务端持有长期密钥并在服务端记录真实 token 用量。

**理由**：只有代理才能观测真实用量、在预算耗尽时拒绝调用、并在流式中断时按实际用量结算。签发令牌模式下服务端永远无法知道客户端用了多少。

**已考虑的替代方案**：
1. 保持直连 + 客户端上报用量。被否决：用量不可信，且客户端崩溃即丢失，无法作为计费依据。
2. 直连 + 上游返回用量。被否决：客户端可篡改，且四类 Provider 的用量上报能力不一致。

**代价**：提示词与 ASR 正文将经过服务端，产品定位从"零留存创作内容"变为"经我方服务端并脱敏留存任务必需数据"。该代价已在 proposal 中列为影响，需要产品口径同步更新。

### 决策二：幂等键为 `(账号, 任务类型, requestId)`，并要求客户端先落盘

**选择**：服务端以三元组唯一约束去重；同键同输入返回原任务，同键不同输入拒绝。客户端付费提交前先在本地事务持久化稳定的 `requestId`、任务类型与输入哈希。

**理由**：只靠 `jobId` 无法覆盖"客户端没收到 `jobId`"这一最常见的中断点；只靠输入指纹无法区分"用户想重试"与"网络重发"。三元组同时给出找回能力与冲突检测能力。

**已考虑的替代方案**：以输入指纹为唯一键。被否决：用户明确想重跑同一内容时会永久复用旧结果，语义过强。

### 决策三：分项预算与"原子预留 + 结果结算"

**选择**：按 ASR 时长、模型 token、图片次数与规格、视频次数与秒数四类分项独立记账。付费提交前原子预留，取得上游结果后按真实用量结算并返还差额。预留后失败则释放预留，只对实际产生的上游用量收费。

**理由**：四类 Provider 的计费单位互不换算，合并成一个余额会导致某一类被另一类挤占。预留保证并发提交不会透支；结算保证不预扣。

**已考虑的替代方案**：只做"次数上限"门禁（现有做法）。被否决：无法覆盖按时长与 token 计费的 Provider，且无法处理"提交成功但结果失败"的部分退款。

### 决策四：待对账状态是独立状态，不是重试

**选择**：已向上游提交但无法确认是否创建成功时，任务进入待对账，保留 `requestId` 与输入指纹，禁止自动重试付费提交；由查询上游或人工处理消解。

**理由**：这是"上游可能已经收钱"的唯一正确姿势。自动重试在不确定状态下必然产生重复付费，而这是不可逆的对外副作用。

**已考虑的替代方案**：自动重试 N 次。被否决：与"不重复付费"的验收标准直接冲突。

### 决策五：受限直传凭证不沿用现有 `public-read` 对象存储路径

**选择**：为临时音频新增受限上传路径，凭证只允许写入单个对象键、带声明大小上限与有效期，对象不永久公开，并按保留策略删除。

**理由**：现有 `S3ObjectStorage` 的上传 + `public-read` + 永久 CDN 地址与 `cloud-asr-provider` 规格的"短期、受控、不得永久公开"直接冲突。

**已考虑的替代方案**：服务端中转上传（客户端上传到服务端，服务端再传对象存储）。被否决：服务端承担全部音频带宽与临时磁盘，且与"客户端直传"的方案目标不符。

### 决策六：网关必须透传流式响应，不做聚合

**选择**：模型网关按到达顺序转发增量、工具调用与结束原因，不缓冲后一次性返回。

**理由**：Harness 与现有三条 LLM 链路都依赖流式增量来表达进度与取消；聚合会引入不可接受的首字节延迟，并使中途取消无法表达。

### 决策七：先冻结契约与门禁语义，Provider 选型后置

**选择**：本次冻结 9 个接口的请求/响应契约、错误分类、门禁语义与记账口径；图片与视频 Provider 的具体选型在实现前单独确认，并纳入服务端版本化配置。

**理由**：契约是客户端三个后续 change 的前置依赖；Provider 选型只影响服务端内部适配层，不改变契约。把二者解耦可以让客户端工作提前启动。

## Risks / Trade-offs

- [隐私定位变更] 提示词与 ASR 正文经服务端 → 服务端只记录完成任务必需的资产引用、用量与脱敏错误；在规格中以独立需求固定"不进入普通日志与遥测"，并在任务中要求可复核的验收证据。
- [上游 Provider 未选型] 图片与视频的时长、规格与配额上限未知 → 契约只声明"任务级动画数量、累计秒数与金额门禁"这三个可配置维度，不写死具体数值；数值在实现前以服务端版本化配置给出。
- [现有计数语义与新分项账本并存] `ai_quotas`、`ai_usage_logs`、`llm_duration_usage_logs` 与新分项账本可能双重计数 → 明确现有三张表继续服务现有 `ai/llm-ak` 与 `ai/duration-usage` 接口，新账本独立命名空间；在迁移计划中要求两边口径一致的交叉校验任务。
- [网关成为单点] 服务端不可用时四类 AI 能力全部不可用（今天客户端本地有 Key 仍可调用）→ 这是"全面切网关"的既定代价，已在决策中确认；通过客户端保留本地 ASR 回退与清晰的预算/网络错误分类来降低影响面。
- [单仓库规格覆盖不到服务端代码] 服务端实现不在本仓库，规格无法约束其内部实现 → 验收以接口行为与账本数据为准，任务中要求跨仓库的可观测证据（接口响应、账本查询结果、清理状态）。
- [流式透传的资源占用] 长连接与背压处理不当会拖垮网关 → 任务中要求并发上限、超时与取消的可验证行为。

## Migration Plan

1. **增量部署**：新增 9 个接口与分项账本表，不修改现有 `activate`、`heartbeat`、`ai/llm-ak`、`ai/quota`、`ai/duration-usage` 的行为。此阶段客户端无需改动，现有功能不受影响。
2. **契约校验**：以本 change 的 delta spec 作为接口行为的验收依据，完成跨仓库的接口级验收。
3. **灰度开关**：新接口按账号白名单开启，未开启账号调用返回明确的未开通错误，不产生付费调用。
4. **对账检查**：上线后核对新账本与现有计数表的口径一致性，确认无双重计数。
5. **回滚**：关闭灰度开关即可退回现状；已产生的任务与账本数据保留，不删除，避免账实不符。
