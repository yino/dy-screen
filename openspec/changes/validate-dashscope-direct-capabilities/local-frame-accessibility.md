# 本地帧到上游可读引用的可达性验证

> 来源：`validate-dashscope-direct-capabilities` 在步骤 0 之后追加的一项验证，2026-09-30。
> 目的：确认客户端直连口径下，**本地视频帧能否成为万相图生视频的 `input.img_url`**。这是与 ASR 音频可达性同性质的问题：客户端直连时，"本地文件 → 上游可读引用"必须逐类验证，不能假定与已有能力同构。

## 1. 背景

`add-generative-video-animation` 的分镜链路要求"参考图提示词以高光内的真实画面为参考来源"。真实链路的第一步是把高光内的本地帧交给万相图生视频。步骤 0 首次验证图生视频时用的是**上游公开示例图**，未覆盖本地帧路径，因此本次补齐。

## 2. 验证素材

从仓库内既有录制素材中取真实帧，与生产链路同性质：

```
源文件  recordings/7663779905489947411/.../20260718-211320.mkv   (真实抖音直播录制)
抽帧    ffmpeg -ss 30 -frames:v 1 -q:v 2  ->  frame.jpg
属性    JPEG baseline / 720x1280 (竖屏) / 92,627 字节
```

## 3. 两条路径的实测结果

万相图生视频的 `input.img_url` 接受**上游签发的签名临时 URL**，不接受 `oss://` 引用。

| 路径 | 构造方式 | 提交结果 |
| --- | --- | --- |
| A：`getPolicy` + 对象存储表单直传 | `GET /uploads?action=getPolicy&model=wanx2.1-i2v-turbo` → 表单直传 → `oss://<key>` | ❌ `InvalidParameter.DataInspection`：`The media format is not supported or incorrect for the data inspection.` |
| B：`/files` 直传 + 取签名 URL | `POST /api/v1/files` → `file_id` → `GET /api/v1/files/{file_id}` → 取 `data.url`（约 927 字符的签名临时 URL） | ✅ 被接受，返回 `task_id` 并进入 `PENDING` |

**结论：路径 B 是唯一可用的本地帧提交方式，与音频直传的三步流程完全同构。**

```
  本地帧/音频文件
      │
      │ POST /api/v1/files                (multipart 直传)
      v
   file_id
      │
      │ GET /api/v1/files/{file_id}
      v
  上游签发的签名临时 URL  ──> 作为 img_url (图生视频)
                          └─> 作为 file_url (文件转写)
```

## 4. 输入规格与失败模式（已用真实录制帧实测）

对真实录制帧做了四组对照，`wanx2.1-i2v-turbo` + `resolution=480P` + `duration=5`：

| 输入帧 | 规格 | 终态 | 产出 |
| --- | --- | --- | --- |
| 录制抽帧 1（竖屏） | `720x1280` | ❌ `AlgoError`（190 秒后） | 无 |
| 录制抽帧 2（竖屏） | `720x1280` | ✅ `SUCCEEDED`（约 200 秒） | `464x832`，5.367 秒 |
| 录制抽帧裁切（横屏） | `1024x574` | ✅ `SUCCEEDED`（约 200 秒） | `832x464`，5.367 秒 |
| 同一横屏帧放大旋转（竖屏） | `1280x2276` | ✅ `SUCCEEDED` | `464x832`，5.367 秒 |
| 上游公开示例图（横屏） | `2048x1365` | ✅ `SUCCEEDED`（约 107 秒） | `768x512`，5.367 秒 |

**关键修正**：两个同为 `720x1280` 的真竖屏帧，一个失败一个成功。因此失败**不是**竖屏规格约束，而是**偶发的上游内部缺陷**，与输入方向无关。这个修正很重要——它把问题从"竖屏不可用"降级为"生成必须按偶发失败设计"，后者成本可控但必须覆盖。

失例的错误是上游内部插帧阶段的空文件缺陷，不是内容审查、也不是引用不可读（引用已被接受并进入 `PENDING`）：

```
TypeError: expected str, bytes or os.PathLike object, not NoneType
  File ".../wanx_pipeline/sora/interpolation/model.py", line 160, in interpolate
```

**已验证的稳定结论：**

1. **产出方向跟随输入方向**：横屏输入 → 横屏产出；竖屏输入 → 竖屏产出。方向由输入决定，不由参数决定。
2. **实际时长恒为 5.367 秒**（请求 5 秒）。五个样例一致，偏差 +7.3% 稳定超过 5% 容差。
3. **分辨率按 `480P` 档位归一**：横屏得 `832x464`，竖屏得 `464x832`，与输入像素尺寸无线性关系。
4. **失败是偶发且与方向无关**：实测竖屏 3 次中 1 次 `AlgoError`（约 33%），横屏 2 次 0 次失败。样本量小，但足以判定该失败模式真实存在且不可由输入预检规避。
5. **失败不返回用量**，但已消耗上游计算时间（失例耗时 190 秒）。

**下游必须据此处理：**

- 生成 MUST 按"偶发上游失败"设计：单条动画失败不视为方案不可行，而应进入可区分错误分类与降级路径。MUST NOT 把 `AlgoError` 归类为"用户内容违规"。
- **重试成本必须由门禁约束**：每次重试都是一次新的付费提交（上游无幂等键），因此重试次数 MUST 计入任务级动画数量与金额门禁，且 MUST NOT 无限重试。
- **失败时长的用户体验**：一次失败要等约 190 秒才得到结论，而成功也需要 107–200 秒。编排 MUST 给该阶段真实的进度与超时预期，并允许用户先审阅已就绪的其他高光。
- 参考帧 SHOULD 在提交前按目标方向做一次归一，避免把方向差异交给上游处理。

## 5. 对实现的影响

1. **图片与视频生成的输入引用统一走"三步直传"**，与 `wire-cloud-asr-upload-and-jobs` 的音频上传实现共用同一套上传原语：`POST /api/v1/files` + `GET /api/v1/files/{id}`。客户端 SHOULD 抽出共用的"上游文件上传"模块，供转写音频、图生视频参考帧与后续媒体输入复用。
2. **`getPolicy` 表单路径对万相也不可用**，原因与转写一致（对象被策略锁定为私有，上游服务读不到）。该路径在 v2 中不应再被任何能力使用。
3. **签名临时 URL 的时效**：实测图生视频耗时在 107–200 秒区间。临时 URL 的有效期必须覆盖生成任务的完整耗时，因此 MUST 在提交前取回，且不得复用过期 URL。
4. **不引入本地帧的公开托管**：参考帧同样属于用户内容，MUST NOT 因此新增公网可读的持久对象。临时 URL 由上游签发并带有效期，符合既有的数据边界要求。

## 6. 与音频路径的对照

| 维度 | 音频（文件转写） | 图片（图生视频参考帧） |
| --- | --- | --- |
| 直传端点 | `POST /api/v1/files` | 同左 |
| 取引用端点 | `GET /api/v1/files/{file_id}` | 同左 |
| 消费字段 | `input.file_url` | `input.img_url` |
| `oss://` 引用 | 不可用（`FILE_DOWNLOAD_FAILED`） | 不可用（`InvalidParameter.DataInspection`） |
| `getPolicy` 表单路径 | 不可用 | 不可用 |
| 结论 | 三步流程可用 | 三步流程可用 |

两项能力的可达性结论一致，可作为同一条实现规则处理，不需要为图片另设路径。
