### 1.3 单次转写流水线（三步直传 → 提交 → 轮询 → 下载）

`/tmp/asr-acc/run_asr.sh <label> <wav>`，核心步骤：

```bash
# (1) 上传

  -H "Authorization: Bearer $AK" -F "files=@$WAV;type=audio/wav"

#     -> data.url（http 签名临时 URL）
# (3) 提交异步转写
jq -n --arg u "$FURL" '{model:"qwen3-asr-flash-filetrans",input:{file_url:$u},
       parameters:{channel_id:[0],enable_itn:true}}' \
 | curl -s -X POST https://dashscope.aliyuncs.com/api/v1/services/audio/asr/transcription \
     -H "Authorization: Bearer $AK" -H "Content-Type: application/json" \
     -H "X-DashScope-Async: enable" --data-binary @-
#     -> output.task_id
# (4) 轮询
curl -s "https://dashscope.aliyuncs.com/api/v1/tasks/$TID" -H "Authorization: Bearer $AK"
#     -> output.task_status == SUCCEEDED, output.result.transcription_url
# (5) 下载结果 JSON（再 GET 一次签名 URL） -> /tmp/asr-acc/results/<label>.transcript.raw.json
```

## 2. 执行过程中发现的偏差：分块时间轴必须修正

**这是本次验收中唯一与任务描述不符的机制点，如实记录。**

任务建议的切片命令是按 `full.wav` 的时间轴写的，但 `full.wav` 本身是 `-ss 60` 切的（`full[0] == mkv[60s]`），
而我实际执行的分块命令是从 **mkv 起点** 切的。两者的时间关系必须显式映射，否则每块句段会整体偏移 48–60s：

| 块 | 切片区间（mkv 轴） | 折算到 full 轴的偏移 |
|---|---|---|
| c1 | mkv [0s, 110s] | `full = c1 - 60000 ms`（可用窗口仅 full [0, 50s]） |
| c2 | mkv [108s, 220s] | `full = c2 + 48000 ms` |
| c3 | mkv [218s, 240s] | `full = c3 + 158000 ms` |

**映射正确性的实测证据**（不是假设，用同一句音频交叉验证）：

- c3 句段 `18860–21980` 「峰哥，你不会去充值了吧。」加 158000 后为 `176860–179980`，与参考句段 `176860–180120` 起点完全一致（Δ=0ms）。
- c1 句段 `57920–62680`「结果把我给困里头了。」减 60000 后为 `-2080–2680`，与参考 `0–3620`「困里头了。」在 mkv [60.0,62.7] 区间重叠，符合 60s 位移。
- 未修正偏移时（错误地按 0/108000/218000 直接相加）合并结果与参考的 `Δbegin` 中位数为 **59980 ms**——该错误值本身就是“偏移未修正”的判据。

**因此本次可用的比对窗口是 full `[0, 180000) ms`**：三块在 full 轴覆盖 `[-60,50]∪[48,160]∪[158,180]`，与参考（full 0–240s）的公共区间为 0–180s。
参考中 `182100 ms` 之后的 5 句落在分块覆盖之外，**不参与比对**（已在下表标记 `OUT`）。
按“不要重复提交/重试”的指令，本次未追加付费调用去补足 240s 覆盖（详见 §6 需 Lead 裁决项）。

**分块设计说明**：任务示例的第 3 块 `236–240s` 只有 2s 新内容、起点落在第 2 块内部，属于“只有重叠区的退化尾块”，按任务要求应并入前一块。
为在保持 3 块（覆盖 2 个重叠边界）的同时避免退化，本次实际采用 `0–110s / 108–220s / 218–240s`，重叠区为 full `[48000,50000]` 与 `[158000,160000]`（各 2s）。

### (d) 重叠边界专项

重叠区：full `[48000,50000]` 与 `[158000,160000]`（各 2s）。

缺陷明细：

| 句段 | 来源 | 时间范围 | 与另句时间交叠 | 文本相似度 |
|---|---|---|---|---|
| 「感慨为。」 | c2（尾句，被切在重叠区内） | 159120–159980 | 740 ms | 0.00 |

只要重叠区两侧 ASR 文本不一致，文本型去重就必然失效。

**补充分析（当时作为修复建议；Lead 随后按此思路实现，重算见 §5(e)）**：若在去重中追加“丢弃完整落在重叠区内的句段”，

若改为“时间交叠且相似度低于阈值时保留时间范围更长者”，效果同上。

### (e) 按修正后的时间交叠消解规则重算（Lead 已实现，2026-09-30 复核）

Lead 已确认 §5(d) 的碎片是真实缺陷，且后果比“重复显示”更严重：产物发布要求句段严格按源时间单调且互不重叠，

已实现的修复（`src/asr/cloud.rs`）：

- `resolve_time_overlaps`（`src/asr/cloud.rs:1093`）：同一路音频内两句段时间交叠时，**保留覆盖更完整者（时长更长者）、直接丢弃较短者**（裁剪只会留下 120ms 级的无意义碎片）；等长保留先出现者。单次前向扫描 + 重新排序，保证输出严格按源时间单调且互不重叠。
- `merge_chunk_segments`（`src/asr/cloud.rs:1052`）在文本去重之后调用 `resolve_time_overlaps`（`src/asr/cloud.rs:1081`）。
- 回归测试 `truncated_boundary_fragment_never_overlaps_neighbour`（`src/asr/cloud.rs:1932`）**直接使用本报告 §5(d) 的真实数据**（159120–159980 vs 159240–162820），并断言任意输入下相邻句段不交叠。

**本次重算未产生任何新的付费调用**：只把 §4.1–4.3 的原始块句段按同一偏移映射回源时间，
然后在 `/tmp/asr-acc/compare3.py` 中**逐语义复刻**上述两个函数——

## 7. 不确定性与限制

1. **比对窗口只有 180s**（提取音频为 240s）。原因见 §2：分块按 mkv 轴切、参考按 mkv+60s 轴切，公共窗口为 full [0,180s)。参考在 182.1s 之后的 5 句未参与比对。
2. **只测了 3 块、2 个重叠边界**，且每块只跑 1 次。第 1 个重叠区（48–50s）两侧都没有产出句段，因此“文本型去重”实际只在第 2 个边界被检验且未命中；**时间交叠消解规则同样只在该边界被真实触发 1 次**（§5(e)），即该规则在真实数据上仅有一个命中样本。
3. **只取自 1 个直播间、1 段直播**（含大量念歌词/唱歌内容，非纯口播），语音分布不代表全部场景。
4. **无法分离 ASR 固有抖动与分块影响**：（b) 中 13 条差异若来自重启识别，则与分块无关；要严格分离需要“同一段音频重复提交”的基线（额外付费调用），本次按指令未追加。
5. 时间对齐结论包含 `-ss` 输入定位的精度影响（帧级，量级 <100ms），与观测到的 40–60ms 中位偏差同量级，无法进一步拆分。
6. 本验收只覆盖句级时间戳；结果中不存在词级时间戳，本报告也未对词级做任何断言。
7. 所有 4 次提交均一次成功（`SUCCEEDED`），无重试、无重复提交；总提交音频时长 240 + 109.96 + 112 + 22 = 483.96s ≈ 8.1 分钟。
8. §5(e) 的重算是**本地复刻**（Python 逐语义对齐 `src/asr/cloud.rs`），不是直接调用 Rust 实现运行；
   复刻覆盖了排序、非法句段过滤、文本归一化（仅去空白）、`dedupe_window_ms=2000`、交叠消解的长短取舍与等长取先。
   若实现后续变更上述任一细节，结论需重算（可用 `/tmp/asr-acc/compare3.py`，无需付费）。
